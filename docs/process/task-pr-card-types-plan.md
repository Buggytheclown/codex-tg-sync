# План Task / PR / Schedule

Дата: 2026-11-11. Ревизия: 3, решение по старым Task-ссылкам подтверждено.
Техническая архитектура ревизии 2 прошла независимое ревью и повторную проверку.
Основание: `task-pr-card-types-spec.md`, согласованный вариант «Единая карточка»
и `task-pr-card-types-spec-review.md`. Приложение и живые данные пока не меняем.

## Результат и границы

На доске остаётся одна запись на карточку. Task получает ручную колонку Review,
PR — единственный основной Арк PR и необязательного родителя Task, Schedule —
явный тип у карточек cron. Под футером Task отображаются строки существующих
PR-карточек; их полные карточки остаются в своих колонках. Официальный статус
Арка показывается только рядом с PR-ссылкой в футере полной PR-карточки.

Не добавляем напоминания, новый механизм запуска, автоматическое завершение
Task, автоматическую линковку по тексту, несколько чатов на запись, дизайн-систему
или новую палитру. Sources остаются Sources. Существующие approval, ownership
TODO → Inbox, независимые правила и Done-хронология сохраняются.

## 1. Данные и инварианты

Сохранить `model.Task` и таблицу `tasks`. Добавить в detail и compact DTO:

| Поле | Смысл |
| --- | --- |
| `card_type` | `task`, `pr`, `schedule` у обычной карточки; пустое значение у Source |
| `arcanum_pr_id` | Канонический положительный ID основного PR; только у `pr` |
| `parent_task_id` | Необязательный ID родительской Task; только у `pr` |
| `pr_status` | Небольшая read-only проекция кеша Арка, отсутствует у других типов |

`source_task_id` и `source_key` сохраняют прежнее значение происхождения и
дедупликации. Не использовать их как связь разработки. `source_url` остаётся
совместимым транспортным полем основной ссылки; у PR оно обязано соответствовать
`arcanum_pr_id`. У Task в нём нет активной PR-привязки; существующий generic
source URL, если это не Арк PR, сохраняется как контекст происхождения.
Schedule сохраняет существующие
необязательные связи и контролы; Арк PR ему не требуется.

Тип фиксируется при создании/миграции. Привязка чата и последующее редактирование
не меняют тип. Обычный редактор создания предлагает Task и PR; Schedule получается
из cron-источника. Source не должен превращаться в обычную карточку и наоборот
через смену polling action: несовместимая смена отклоняется сервером.

В таблице: CHECK допустимых типов и формата nullable полей, self-FK
`parent_task_id REFERENCES tasks(id)`, индекс parent ID, частичный UNIQUE
по непустому `arcanum_pr_id` у PR. Межстрочное условие «родитель именно Task»
проверяется транзакционно в storage. Нет удаления карточек в текущем API;
при будущей реализации удаления потребуется явная политика отвязывания.

Review разрешён только обычным Task. Расширить модель колонок, storage-валидацию,
move/reorder/create и UI. Sources, PR и Schedule туда не переносятся. Поллинг
никогда не переводит Task в Review или из Review в Done: активен только Polling,
а Review — ручное состояние. Родитель не получает состояние от детей.

Изменение связи увеличивает только версию PR и пишет событие его History.
Метаданные Арка не меняют editable version/updated_at карточки и даты Done.
Обычные редактирования с отсутствующими новыми полями сохраняют тип и связь.

## 2. Создание и единственность PR

Вынести канонический parser PR ID/поддерживаемых Arc URL в общий существующий
слой валидации. Он не ходит в сеть; URL строится только из проверенного ID.
Использовать один механизм в manual create, source outcome, legacy import и
редактировании основной ссылки. Не разбирать названия/эмодзи для identity.

Порядок в транзакции создания обычной PR-карточки:

1. Разрешить тип и PR ID; проверить входные ограничения и source/thread identity.
2. Найти PR по каноническому ID, независимо от Source namespace.
3. Если найден — вернуть/использовать существующую запись. Не переносить чат,
   parent, config, source provenance, колонку или дату Done из нового шаблона.
   Если входной обязательный thread/source identity указывает на другую запись,
   вернуть конфликт; не объединять чаты или записи.
4. Если не найден — создать обычную карточку и её polling как сейчас; UNIQUE
   индекс остаётся последней защитой. При конфликте reread в новой транзакции
   и тот же исход; не пытаться повторно выполнить запуск.

В `AcceptTaskPollingOutcome` сначала сохраняются нынешние task/column/generation
и event-key guards. Существующий PR становится `result_task_id` события, но
`target` для нового initial launch отсутствует. Новое discovery само не запускает
его, не переставляет и не переписывает настройки. Собственные правила уже
созданного PR обслуживают последующие раунды. Это сохраняет текущую семантику
ветки повторного source key, расширяя identity между источниками.

При legacy import не перепривязывать исторические requests к чужому чату, если
канонический PR уже существует с иной thread identity: остановить конфликтный
импорт до изменений, выдать диагностируемый конфликт. Безопасное объединение
исторических чатов не входит в задачу.

`TaskDefinition` получает тип создаваемого ребёнка. PR review/feedback нормализуют
его в `pr`, cron — в `schedule`; несовместимое явное значение отвергается.
Валидировать PR ID после подстановки event variables, а не требовать конкретный
номер в ещё не материализованном шаблоне Source. Существующие определения без
поля нормализуются по семейству Source. Add chat без типа создаёт Task, но
идемпотентное нахождение уже привязанной карточки сохраняет её прежний тип.

## 3. Редактирование и связь разработки

Добавить узкую операцию `SetTaskParent` через storage → tasks → daemon/board
→ controlapi. Контракт: `expected_version`, `parent_task_id` (пустое — снять).
Ответ — компактная PR-карточка. В одной транзакции: прочитать PR/версию,
проверить существование родителя и его тип Task, сохранить связь, history,
увеличить версию. Повтор той же связи без устаревшей версии — no-op. При
устаревшей версии вернуть обычный 409 и актуальное чтение, не теряя UI draft.
Перепривязка — такая же явная операция, максимум один parent ID.

Доступны поиск существующей Task из PR и выбор PR из Task. Обе формы вызывают
одну операцию над PR; новый bulk API и отдельная таблица связей не нужны.
Выбор родителя не зависит от текущего фильтра доски. UI использует весь compact
snapshot для кандидатов; разрешён только тип Task. Создание PR и связывание
можно выполнить последовательно: при ошибке связи остаётся доступный отдельный
PR, а форма предлагает повторить линковку без повторного создания карточки.

У Task API отвергает непустую основную PR-ссылку; у PR — Tracker и очистку PR ID.
Существующий Ticket command также проверяет тип, обход через прямой запрос
не допускается. PR-ссылка в другом поддерживаемом формате с тем же ID не меняет
identity/курсор. У PR с происхождением PR Source (durable source key либо
source provenance) номер неизменяем: другой PR создаётся/выбирается отдельной
карточкой. Иначе старый source key с номером A продолжал бы указывать на B.
Ни форматирование URL, ни ручная смена родителя не снимают это ограничение.

У ручного PR без такого происхождения смена номера требует UNIQUE и НОВЫХ
защит, аналогичных существующему `LinkTaskChat`. Сейчас обычный `UpdateTask`
таких защит не имеет. При фактической смене ID daemon читает authoritative
состояние связанного чата вне launch gate и отвергает active/waiting/неизвестное
состояние. Затем под `taskLaunchMu` повторно проверяет expected version,
неизменность исходного PR/thread и отсутствие незавершённых, pending или uncertain
requests; storage повторяет транзакционные guards и сохраняет ссылку с rules
атомарно. Не брать syncMu после taskLaunchMu. При недоступной authority смена
номера не разрешается; обычный autosave и same-ID URL edit этого IO не требуют.
Защита применяется к прямому PATCH и combined workflow, не только к footer форме.

Смена PR ID не перенастраивает правила автоматически. Если сохранённые
`pr_wait`/PR-листья rules относятся к другому ID, операция отклоняется с понятной
ошибкой. Согласованную замену ссылки и правил можно сохранить одной существующей
workflow-операцией; она сбрасывает cursor и повышает generation как сейчас.
Правила с явной ссылкой на другой PR у PR-карточки не принимаются и при отдельных
сохранениях polling. У Task/Schedule сохраняется прежняя возможность настраивать
ожидание внешнего PR. Обновление identity и polling атомарно, в том числе при
ошибке записи. Не отменять и не переписывать frozen requests молча.

## 4. Пассивный статус Арка

Добавить небольшой кеш в SQLite, ключ — `arcanum_pr_id`, поля: lifecycle,
common_status, last_attempt_at, last_success_at, last_error, next_check_at.
Не хранить в нём комментарии, checks или prompt. Полный и compact DTO читают
одну проекцию: raw-статусы, подтверждённое display value, даты и availability.
Санитизированная ошибка доступна как недоступность/tooltip, без сырого CLI вывода.

Добавить отдельный metadata reader в `internal/arcanumreview`, пользуясь уже
доказанными командами: `pr get` для ID/lifecycle/author и `pr search author(...)`
с `--all` и минимальными `id,common_status`. Merged может завершаться после get.
Не предполагать поддержку `common_status` в v2 get или непроверенного поиска
по ID. Не вызывать `pr comments`/checks ради футера. Существующий полный
`ReadPRSnapshot` для правил сохраняет необходимые факты и ошибки; допустимо
вынести общий decode/helper без изменения его контракта.

Перед UI mapping проверить raw-значения по официальному CLI/доступному read-only
ответу и существующим fixtures. Известные значения отображать терминами Арка.
Неизвестное непустое значение сохранять и показывать как неизвестный raw-статус,
не превращать в Ready to merge; пустой/неполный ответ — ошибка наблюдения.
Это ограниченный исследовательский шаг перед mapping, не основание менять API.

Один последовательный background worker вне writer lock Sync и вне выполнения
правил. На старте демона запускается с общим ctx; не задерживает startup и не
зависит от открытого браузера/Sync enabled. Читает только ID реальных PR-карточек
из due queue, ограниченными порциями по 10, в порядке next_check_at + PR ID.
Сетевой IO происходит вне SQLite транзакции. Контекст одного metadata чтения
ограничен 15 секундами; shutdown отменяет его.

Начальное значение периода — 5 минут во всех колонках, включая Done (PR может
быть переоткрыт). После попытки, успешной или нет, next_check_at = now + 5 минут;
новая привязка ещё не наблюдавшегося PR становится due сразу. Это best-effort
период, не обещание максимальной задержки при недоступном API. Ожидаемый объём
текущей доски — десятки PR; повторяющиеся строки/вкладки не создают новых jobs.
Worker дренирует due порциями без дополнительной пятиминутной паузы между
порциями; при отсутствии due ожидает ближайший срок/короткий cancellable tick.

До успеха — нейтральный placeholder. После ошибки — последнее подтверждённое
значение с stale-маркером; без предыдущего — unavailable. Возраст больше
10 минут также считается stale, даже если worker/демон не работал. Последующие
успешные наблюдения снимают marker. Ошибки metadata не создают Telegram launch
или новые Telegram health notifications: это представление, не новый action poller.

Запись кеша адресуется ID наблюдённого PR, а не карточке. Поздний ответ старого
PR не может попасть к карточке после смены её ID. Один worker не допускает
перестановки своих наблюдений. Не добавлять запись статусов из rule runner,
пока нет отдельной необходимости и fencing для нескольких writers.

Metadata reader никогда не вызывает `AcceptTaskPollingOutcome`, не обновляет
cursor/generation/event/request, не создаёт запуск и не двигает карточки.
Ошибки пассивного чтения не блокируют обычные правила. Правила продолжают
читать свои полные свежие snapshots; не подставлять пятиминутный кеш в условия.

## 5. Компактная доска и UI

Расширить `taskColumns`, insert/scan/full read и compact query. В compact query
одним LEFT JOIN подключить кеш; parent ID уже в tasks. Сохранить нынешние две
ограниченные SQL-выборки без чтения config/frozen prompt/snapshot JSON.
Никаких запросов detail на строку и сетевого Arcanum IO внутри HTTP GET.
SSE уже хеширует полный компактный JSON: статус/parent попадут в revision без
искусственного увеличения editable версии.

В `ui/src/model.ts` расширить Task/TaskCard и `compactTask`; единый normalized
snapshot — источник обеих визуализаций. Сначала собрать `childrenByParent`
из ВСЕХ обычных карточек, затем применять поиск/фильтр для самостоятельных
карточек. Родительская строка использует child ID/PR ID/column из того же
snapshot, включая оптимистический move и rollback. Не хранить отдельную
копию child-state внутри Task. Поиск по source PR URL/ID и Tracker сохраняется.

Карточка: тип TASK/PR/SCHEDULE независимо от наличия чата; все текущие данные,
приоритет, execution/polling indicators и Codex-контрол сохраняются. Footer
Task = Tracker + Codex; PR = Arc ссылка/редактор + Arc status + Codex.
Под footer Task — отдельные доступные кнопки `#PR — Polling/TODO/Inbox/Done`,
без остальных полей. Не вкладывать кнопку в кнопку выбора карточки.
Нажатие/keyboard activate выбирает child, pointerdown не начинает parent drag;
подстроки не являются drag handles. Высота всего wrapper, включая строки,
входит в имеющиеся измерения drag placeholder и анимации.

В Overview PR — компактный контрол родительской Task и переход к ней. Выбор
родителя открывает детали Task, её Codex-контрол ведёт к её чату; чат PR не
перепривязывается. Сохранить глубокие ссылки, выбор скрытых поиском/Done карточек,
защиту stale detail responses, dirty drafts и прежнее отсутствие footer в details.
Связями управляют эти Overview-контролы, дополнительные кнопки в строках не нужны.

Добавить Review между TODO и Polling: Inbox / TODO / Review / Polling / Done.
Семантическое соответствие иконок/состояний вместо индекса массива. Списки
доступных destination фильтруются по типу; drag PR/Schedule в Review запрещён.
Desktop grid имеет 5 колонок (4 при скрытой Done). На средних ширинах не сжимать
карточки ниже текущего минимума: содержимое board прокручивается горизонтально
внутри своей области, не перекрывая inspector. Узкие breakpoints сохраняют
текущую раскладку. Done drop target не меняет свою зарезервированную ширину.
Сохранить палитру и motion, проверить reduced motion, focus outline, hover scroll.

## 6. Миграция без потери истории

### Схема

SQLite CHECK у tasks сейчас не допускает Review. После существующих upgrades
source definitions/Done добавить отдельную идемпотентную миграцию с marker.
Свежая БД сразу создаёт новую схему; старую перестроить один раз.

Миграция старой базы запускается только отдельной offline-командой; обычный
startup сначала делает read-only preflight и сообщает, что нужен dry-run/apply,
если marker отсутствует. Он не выполняет generic backfill до проверки карты.
Свежая пустая база не требует частной карты.

В apply взять dedicated `sql.Conn` до BeginTx; PRAGMA foreign_keys=OFF
выполняется вне транзакции. В транзакции создать tasks_new, скопировать все
колонки/ID с backfill, удалить старую tasks и переименовать новую. Не переименовывать
сначала оригинал: SQLite может переписать ссылки зависимых таблиц на старое имя.
Восстановить существующие и новые индексы, проверить FK через foreign_key_check,
поставить marker, commit. На любом исходе восстановить foreign_keys=ON на том
же соединении до возврата его в pool. Любая ошибка откатывает всю миграцию.
Не использовать writable_schema. Не пересоздавать task_events: его rowid участвует
в ownership ручных переносов. Не трогать frozen requests, cursor и generation.

### Классификация и карта

Точка входа — `ctr-go board migrate-card-types --dry-run` и
`ctr-go board migrate-card-types --apply <private-report-path>`.
Dry-run открывает БД read-only напрямую, без обычного Store initialization,
и не вызывает schema upgrades. Он пишет частный JSON-отчёт с format version,
фиксированной policy `archive_task_pr_reference`, текущими ID/version/классификацией и digest
значимых исходных данных/Source definitions. Точный путь задаёт оператор;
публичные fixtures синтетические. Apply требует остановленного демона и передаёт
validated migration options в storage до любых изменений карточек. Повторный
startup после успешного marker работает как обычно, без report input.

Перед будущим применением получить свежую частную карту: ID, version и поля,
определяющие классификацию. Действующая карта — проверенный снимок, не код
для безусловного применения. Формат отчёта закрытый и versioned: действия карты
ограничены типизацией и согласованным переносом ссылок в History;
никаких SQL, shell или произвольных task patches из input. Никаких реальных идентификаторов/личных ссылок
или жёстко зашитых исключений в публичном репозитории.

При backfill сначала отделить Source по create_task action. Для обычных:
PR review/feedback provenance/source key/тип родительского Source → PR;
cron provenance → Schedule; остальные → Task. UI-иконки используют эти же
признаки, поэтому текстовые значки в произвольном title не основание.
Для PR извлечь ID из действующей ссылки, проверить отсутствие конфликтов.
Очистить запрещённый Tracker у PR, сохранив прежнее значение в History.
При отсутствующем/невалидном ID или реальной коллизии PR с разными чатами
прекратить apply до изменений; не угадывать и не объединять.

Пользователь 2026-11-11 подтвердил policy `archive_task_pr_reference`:
у каждой старой ручной Task с прямой Арк PR-ссылкой одно history-событие
сохраняет прежние PR ID / URL и причину отвязки, затем активный source_url
очищается в той же транзакции. Generic source URL не очищается. Существующие
отдельные PR остаются без автоматически установленного parent; частная карта
хранит только предложения ручного связывания. Apply не устанавливает связи.
Общий backfill покрывает и отдельно согласованную ручную отвязку: новую
PR-карточку не создавать, чат не переносить. Индивидуальные команды связывания
и жёстко зашитые частные исключения миграции не нужны.

Сначала dry-run и полный validation карты, затем один atomic apply. На остановленном
демоне сверить версии ВСЕХ затронутых записей и source definitions; при изменениях
пересобрать dry-run, не перетирать актуальные поля. Digest охватывает полный
набор карточек и связанные определения, поэтому появление новых карточек тоже
делает старый apply недействительным. Apply перечитывает эти условия внутри
транзакции перед первым data/DDL изменением миграции. Решения по типу и legacy references входят в ту же schema/data transaction,
чтобы до завершения перехода не обслуживалась наполовину мигрированная доска.
После apply повтор той же карты/marker — no-op, не дублировать history и связи.

Перед запуском сохранить корректную SQLite backup через backup API либо offline
после закрытия БД с учётом WAL. Сравнить ID/count/type, thread IDs, states/Done,
history rowids, source keys, requests и polling generations до/после. Новая схема
не поддерживается старым бинарём; rollback = восстановить backup и старую версию,
а не открыть новую БД старым процессом. Не откатывать поверх новых пользовательских
изменений без отдельного согласования.

## 7. Порядок реализации

Все шаги — одна поставка без промежуточного обновления пользовательского демона.
Выбор перехода старых Task закрыт; dry-run/apply используют согласованную policy.

1. **Схема, модель, классификация, Review.** Тесты old/fresh DB и dry-run migration;
   затем поля/scan/DTO/колонки/валидация. Проверить rollback и FK, сохранение
   источников, Done и task_events rowids. Это минимальное внутреннее приращение,
   до полного UI не выкатывается.
2. **Identity на всех путях создания.** Parser, UNIQUE, manual/source/import,
   тип child definitions. Проверить две Source семьи на один PR, конкуренцию,
   конфликты thread identity и отсутствие лишнего launch. Настроенные правила
   старого PR продолжают работать с тем же чатом.
3. **Ручные связи и UI.** Операция parent, формы выбора, нормализованная проекция,
   строки, Review, типизированные footers и поиск. Проверить доступность,
   конфликт/rollback и незацикленную навигацию между двумя разными чатами.
4. **Пассивные метаданные.** Тест metadata reader до реализации, verified status
   mapping, кеш/worker/композиция в main, JOIN/SSE/footer. Отдельно доказать
   отсутствие action/cursor/generation/launch при чтении вне Polling.
5. **Полная приёмка и подготовка обновления.** Интеграционные сценарии ниже,
   fresh-context review diff/tests, обновление ADR-035, regression-map и contracts.
   Установку, реальное применение частной карты и запуск выполнять только в
   рамках отдельного запроса на реализацию/обновление.

## 8. Проверка требований

| Спека: проверяемый результат | Механизм и отличающая проверка |
| --- | --- |
| 1, 12 | Type backfill/create + UI; чат не меняет тип, PR не принимает Tracker, Task не принимает PR, Source не мигрирует |
| 2, 3, 7 | Один parent ID + строки одного compact snapshot; 3 PR в разных колонках, unlink/reparent/reopen без копий и переноса чатов |
| 4 | Единое состояние клиента + transactional move; optimistic success/error, SSE во время save, stale version, оба представления одинаковы |
| 5, 6 | Metadata worker/cache; внешний статус меняется в TODO/Inbox/Review-independent UI, ошибка/stale/restart/late old-ID response; ноль effectful calls |
| 8 | childrenByParent до фильтра; PR ID и оба URL host formats, Tracker ID/URL; родитель найден без совпадения child; counts не включают строки |
| 9 | Global PR UNIQUE + повторное discovery обоими sources и после restart; одна карточка, прежний чат, frozen requests неизменны |
| 10 | Task-only Review + отсутствие aggregate move; все PR merged/Done, Task остаётся Review, только manual Done задаёт done_at |
| 11 | Существующие polling outcome + request pipeline; pending approval уже TODO, approve продолжает прежний thread, terminal возвращает только owned TODO |
| 13, 14 | Version-fenced private apply + history; ссылки архивируются и активное поле очищается до ручной связи, обе записи/чаты/Done сохранены; повтор не дублирует history, apply не создаёт parent/PR/chat |

Дополнительно: PR URL+rules replacement атомарен; invalid/duplicate/clear/pending
случаи сохраняют draft и прежнее состояние. У source-owned PR смена номера
отвергается, same-ID URL edit проходит; после этого повторное discovery исходного
PR не даёт конфликтующих source/PR identities. У ручного PR обе update-формы
не допускают смену при pending frozen request, uncertain dispatch, active chat
или недоступной authority; race update/claim имеет один определённый исход.
Dry-run и обычный запуск до apply не меняют старую БД, подмена/устаревание
report и ошибка DDL отклоняются без частичного перехода. Старый клиент с omitted новыми
полями не удаляет связи. Изменения Source не переписывают уже созданные PR.
Проекция выполняет прежнее ограниченное число запросов и не загружает большие
payloads; множество родительских строк не умножает metadata jobs.

Во время реализации: сначала targeted storage/tasks/controlapi/polling/arcanumreview
и UI tests, затем `go test ./...`, соответствующие race tests, `go build
-buildvcs=false ./...`, `npm test`, `npm run build`, `git diff --check` и
секрет/local scan из AGENTS.md. Browser QA на изолированных fixture cards:
широкая/узкая доска, drag/footer/строки, фокус, select, keyboard, поиски, Done,
details motion и drafts. Telegram-facing регрессии — live QA существующего Sync
контура только на тестовых задачах/чатах, без изменения реальных PR.

## 9. Почему такой объём

Один parent ID проще общей relation/subtask модели: кардинальность уже задана,
нет рекурсии и групповых операций. Строка проецирует существующий PR, поэтому
не нужны синхронизация копий и отдельный счётчик подзадач.

Отдельный статусный кеш/worker требует небольшой новой части, но использует
готовый CLI и не смешивает видимость Арка с правом запускать работу. Встроить
статус в action poller меньше по строкам, однако вне Polling пришлось бы обходить
его защиту либо нарушить свежесть. Полный snapshot только ради footer добавлял
бы чтение всех комментариев. Общий stale cache для правил уменьшил бы запросы,
но ослабил бы согласованность событий; для первой реализации он не нужен.

Тип в общей таблице сохраняет существующие ID/requests/history и компактную доску.
Три отдельные таблицы/миграция чатов дороже без дополнительной гарантии.
SQLite rebuild неизбежен из-за действующего CHECK; временная подмена Review
другой колонкой разрушила бы требование и ownership.

Готовность: план готов к реализации, продуктовые вопросы закрыты. Политика
перехода старых Task-ссылок подтверждена. Статусный mapping имеет ограниченный read-only шаг проверки
до реализации mapping; остальной код не зависит от новых возможностей API.

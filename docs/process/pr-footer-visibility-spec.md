# Обновление статусов PR только при активной доске

Дата: 2026-11-11. Статус: требования подготовлены; определение активности
подтверждено пользователем. Это спецификация, реализация ещё не выполнена.

## Цель

Не обращаться в Арк ради статусов футеров, когда пользователь не смотрит доску.
При возвращении сразу начинать получение актуальных статусов. Рабочие правила
поллинга и Sources продолжают работать независимо от открытой страницы.

## Исходное поведение

По текущему коду `internal/arcanumreview/metadata.go` и
`internal/storage/store_pr_metadata.go` демон обновляет отдельный кеш метаданных
всех PR-карточек независимо от открытых страниц и колонки, включая Done.
Следующая попытка назначается через пять минут после предыдущей. Чтения
последовательные, между карточками выдерживается двухсекундная пауза.

Обновления списка карточек через HTTP/SSE не являются обращениями в Арк.
Остановка только браузерного таймера не решает поставленную задачу.

## Требуемое поведение

1. Активность страницы управляет только пассивным получением метаданных PR
   для футеров. При отсутствии активных страниц доски новые такие чтения
   не начинаются. Закрытая доска также не считается активной; запуск демона
   сам по себе не разрешает чтения статусов.
2. Страница активна, когда вкладка видима и окно не свёрнуто.
   Переключение фокуса в другое окно само по себе не отключает видимую доску.
   Скрытая вкладка или свёрнутое окно считаются неактивными.
3. Первое открытие доски и переход от отсутствия активных страниц к наличию
   хотя бы одной сразу инициируют обновление статусов всех PR-карточек,
   включая недавно обновлённые. Ждать окончания прежнего пятиминутного
   интервала не нужно. Пользователь сразу видит имеющиеся данные, затем
   результаты поступают по мере чтения.
4. «Сразу» означает запуск очереди без ожидания периодического срока, а не
   одновременные запросы для всех ПРов. Сохраняются последовательное исполнение,
   существующие паузы и ограничения чтений. Завершение всей очереди зависит
   от количества ПРов и скорости Арка.
5. Пока есть активная страница, сохраняется нынешняя периодичность: следующая
   плановая попытка для ПРа через пять минут после предыдущей попытки.
   Состав обновляемых карточек также сохраняется: все PR-карточки, включая
   Done, независимо от поиска, прокрутки и свёрнутости колонок.
6. Несколько активных вкладок или окон используют одно обновление. Открытие
   второй вкладки при уже активной первой не инициирует дополнительный обход.
   Повторные сигналы активности не перезапускают выполняющееся чтение и не
   накапливают отдельные обходы. При возвращении во время незавершённого обхода
   продолжается одна очередь без повторной постановки уже ожидающих чтений.
7. Когда последняя активная страница становится неактивной, новые чтения
   прекращаются, включая оставшиеся элементы уже выбранной очереди.
   Начавшееся чтение может завершиться и сохранить результат. Остановка не
   считается ошибкой Арка и не создаёт уведомлений в Telegram.
8. Закрытие, аварийное завершение браузера и потеря связи не должны оставлять
   бессрочное разрешение на фоновое обновление. После восстановления связи
   активная доска снова инициирует получение актуальных статусов. Конкретный
   механизм обнаружения и ограниченный срок потери активности определяются
   в плане реализации.
9. На паузе последнее подтверждённое значение сохраняется. Действующие правила
   stale/unavailable остаются прежними: пауза сама по себе не является неудачной
   попыткой, возраст данных не сбрасывается. Ошибка после возвращения сохраняет
   последнее успешное значение и нынешнее обозначение проблемы; плановый
   повтор остаётся через пять минут. Ошибка не блокирует обновление других ПРов.
10. Получение статуса не меняет карточку, её редактируемую версию, историю,
    поллинг, курсоры событий, привязанный чат или launch request. Пассивное
    чтение по-прежнему не запускает промпты и не перемещает карточки.

## Границы

- PR waits, cron, Sources, Telegram approvals и запуски Codex работают без
  открытой доски по прежним правилам. Они могут обращаться в Арк и при
  неактивной странице; требование не означает ноль всех запросов в Арк.
- Дедупликация чтений между рабочим поллингом и кешем футеров в эту задачу
  не входит.
- Не меняются внешний вид, элементы управления, статусы Арка, модель карточек
  и действующие правила свежести данных.
- Общую приостановку HTTP/SSE и остальных обновлений доски не вводим ради
  этой задачи. Их доставка не должна давать разрешение на чтения Арка от
  скрытой страницы.

## Проверка результата

- При запуске демона без открытой доски пассивных чтений PR нет; рабочий
  поллинг продолжает выполнять настроенные проверки и действия.
- Открытие активной доски инициирует обход без ожидания пяти минут. Повторное
  открытие после ухода также обновляет PR, успешно проверенный недавно.
- В активной доске после завершения обхода действует прежняя периодичность
  и пауза между PR; статусы появляются постепенно без параллельного всплеска.
- После ухода с последней активной страницы новый PR из очереди не читается,
  даже если очередь уже была получена. Результат начавшегося чтения допустим.
- Две активные страницы не удваивают количество проверок. Уход с одной из
  них не останавливает обновления, пока вторая активна.
- Потеря фокуса видимым окном не останавливает обновление. Переключение на
  другую вкладку или сворачивание последнего видимого окна ставит его на паузу;
  возвращение вкладки или разворачивание окна инициирует обновление.
- Быстрые переключения не создают параллельных чтений одного PR и очереди
  одинаковых обходов. Разрыв связи и закрытие браузера прекращают разрешение
  за ограниченное время; восстановление активной страницы возвращает работу.
- Ошибка отдельного чтения сохраняет последнюю успешную информацию и не
  мешает остальной очереди; пауза не записывает фиктивную ошибку.
- Карточки не перемещаются, чаты не запускаются и курсоры событий не меняются
  вследствие открытия, скрытия или восстановления страницы.

## Открытые вопросы

Продуктовых вопросов не осталось. Механизм передачи активности и ограниченный
срок обнаружения потери связи определяются в плане реализации.

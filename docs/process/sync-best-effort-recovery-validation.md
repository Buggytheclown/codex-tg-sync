# Проверка best-effort Sync recovery

Дата: 2026-11-07. Изменения закоммичены и установлены локально. Бинарник собран
из изолированного снимка коммита без посторонних правок рабочего дерева.
Перед обновлением сохранены резервные копии бинарника и SQLite. Публикация
в remote не выполнялась.

## Реализовано

- Журнал всех путей создания топиков: discovery/activation, project drafts,
  внешние запуски. Unknown одной цели не останавливает остальные и не повторяется.
- Служебные события собственного бота сохраняются до polling acknowledgement.
  Восстановление использует точное отправленное имя; неоднозначность и возможный
  дубль сообщаются в Control. Подтверждённая привязка не заменяется по имени.
- Подтверждение и materialization атомарны; повтор не создаёт использованный
  draft заново. Ошибка SQLite сохраняет возможность восстановления без повторного
  remote create. Legacy markers превращаются в консервативные отдельные unknown.
- Off/force не прерывают Codex и не отвечают на approvals/input. Отображение
  удаляется отдельно от execution rows и writer leases. Поздний topic creation
  закрытой сессии попадает в cleanup. Очистка повторяется в состоянии off.
- Обычные Telegram-команды обрабатывает один worker. Небольшой специализированный
  SQLite inbox сохраняет вход до acknowledgement и позволяет off обойти команду,
  ожидающую IO. Это поддерживающее уточнение плана: очереди только в памяти было
  бы недостаточно для сохранности входа при раннем acknowledgement.
- Off отменяет ещё не отправленные старые inbox-команды. Порядок update IDs
  защищает от запоздавшего on. После рестарта processing-команды становятся
  неизвестными без повторного исполнения; их нижележащие receipts/intents
  восстанавливаются отдельно. Control получает объяснение.
- RPC frame admission остаётся под lifecycle lock; start/steer response wait
  освобождает его. Внешние запуски освобождают оба gate с сохранением порядка
  захвата и защищаются от второго worker на тот же request.
- External draft зарезервирован до claim исходного запроса. Закрытый request
  не запускается после позднего подтверждения топика.
- Legacy draining при startup переходит в off без новых interrupt.

## Автоматические проверки

Выполнены:

- `go test ./...`;
- `go build -buildvcs=false ./...`;
- race-тесты пакетов `internal/appserver`, `internal/storage`, `internal/daemon`,
  `internal/telegram`;
- `git diff --check`, repository secret/local-pattern scan и проверка новых
  файлов на приватные пути и идентификаторы исходного инцидента;
- проверка синтаксиса opt-in Python probe.

Основные различающие регрессии:

- один unknown не мешает следующему чату, в том числе после открытия БД заново;
- одинаковые имена и legacy unknown без исходного имени не дают догадочной привязки;
- SQL-trigger failure при binding откатывает транзакцию, сохраняя известный ID;
- позднее подтверждение при off создаёт cleanup target;
- повтор confirmation после удаления/использования draft не создаёт его снова;
- ошибка записи service event не продвигает getUpdates offset;
- через настоящий `Bot.Run` off фиксируется до возвращения задержанного create,
  а поздний созданный топик остаётся только целью очистки;
- retained writer не закрывается по старому terminal-снимку, включая unknown
  dispatch без известного turn ID;
- подходящий terminal для известного хода освобождает retained writer;
- ожидание внешнего IO освобождает оба mutex, а response wait освобождает
  lifecycle lock после отправки frame;
- uncertain processing inbox не повторяется после recovery, старый on не
  пересекает записанный более поздний off.

Свежий reviewer проверял спецификацию, план и совокупный diff несколькими
проходами. Найденные ошибки порядка блокировок, повторного исполнения inbox,
повторной materialization и startup ordering исправлены. Последний проход
не выявил новых существенных замечаний.

## Живые проверки и ограничения

На текущем общем App Server выполнены два изолированных protocol probe:
`item/tool/requestUserInput` и `item/commandExecution/requestApproval`.
Второй клиент успешно подписался на тестовый чат, получил ожидающий запрос,
ответил на него; исходный ход завершился. Writer connection сохранялся.
Тестовые постоянные чаты архивированы. Сам интерфейс Desktop этим экспериментом
не проверялся: подтверждена передача через тот же App Server protocol.

Воспроизводимый probe: `tests/probes/pending_requests.py --url <shared-websocket>
--kind input` либо `--kind approval`. Он требует Python с `websockets`, создаёт
собственный тестовый чат, выполняет один безвредный tool action и архивирует чат.

После обновления установленного демона выполнена проверка через его единственный
рабочий getUpdates consumer. Для изолированной операции закрытой тестовой сессии
создан временный топик; результат HTTP не передавался демону. Подтверждено:

- собственное `forum_topic_created` получено и сохранено;
- три мигрированные unknown-операции без исходного имени сохраняют предусмотренную
  консервативную неоднозначность; уведомление для тестовой операции записано в Control;
- после передачи удержанного ID как позднего ответа демон сам подтвердил операцию
  и удалил тестовый топик закрытой сессии;
- состояние active и ID рабочей Sync-сессии сохранились, демон вернулся в ready,
  последняя ошибка пуста; команды бота ограничены заданной группой.

Это проверяет реальный приём события, обработку неоднозначности, позднее
подтверждение и cleanup. Автоматическая привязка исключительно по имени при
отсутствии legacy fences на рабочем контуре этим экспериментом не проверена;
она покрыта локальными тестами. Полный UI-сценарий off/on с удалением пользовательского
отображения ради приёмки не выполнялся.

Для отдельного бота добавлен `TestLiveLostTopicCreateResponse`, запускаемый только
при явно заданных `CODEX_TG_PROBE_EXCLUSIVE_BOT=1`, `CODEX_TG_PROBE_BOT_TOKEN` и
`CODEX_TG_PROBE_GROUP_ID`. Нужен бот без другого getUpdates consumer. Probe теряет
успешный HTTP-ответ на create, проверяет собственное событие и удаляет свой топик.

Изолированный снимок коммита прошёл `go test ./...` и сборку. В первом прогоне
однократно упал существующий `TestDeliveryQueueDeadCount`; повтор этого теста
пять раз и повтор полного набора прошли. Посторонний тест не изменялся.

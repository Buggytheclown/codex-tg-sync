# Task / PR / Schedule: тип карточки, Ревью и связи

Статус: типы, визуальные решения, жизненный цикл и ручные связи согласованы.
Правила перехода старых карточек уточнены; частная карта подготовлена отдельно
от публичного репозитория. Дата: 2026-11-11.
Документ описывает требуемое поведение, а не уже выполненную реализацию.

## Цель

После разработки пользователь видит, какие ПРы ещё ожидают ревью, и может из
карточки исправлений вернуться к исходной задаче и её чату. Завершение отдельного
запуска Codex, состояние карточки и состояние ПРа в Арке различаются явно.

## Принятые решения

1. У обычной карточки есть явный тип `Task`, `PR` или `Schedule`. Эти подписи заменяют
   нынешнее определение `CHAT` / `TASK` по наличию чата. Привязка, смена или
   отсутствие чата не меняет тип. Sources остаются отдельными источниками.
2. У `Task` есть связь с тикетом Tracker, но нет собственного поля Арк ПРа и
   действия Add PR. У `PR` есть основной Арк ПР, но нет собственного поля Tracker
   и действия Add ticket. Оба типа сохраняют название, описание, приоритет,
   привязанный чат, настройки исполнения, поллинг и историю.
3. У Task появляется колонка `Review` — «Ревью». Существующие Inbox, TODO,
   Polling и Done сохраняются. Разработка может оставаться в Review, пока
   связанные PR-карточки находятся в разных состояниях.
4. Полные PR-карточки видны на доске независимо от связей с Task. Связь с задачей
   не обязательна для существования PR-карточки.
5. Связанные ПРы показываются в принятом варианте «Единая карточка»: внутри
   нижней части карточки Task, непосредственно под её существующим футером.
   Тело карточки, приоритет, описание, индикаторы и футер сохраняют текущий стиль.
6. Каждый связанный ПР занимает одну кликабельную строку: `#<Арк PR> — <состояние
   нашей PR-карточки>`. В строке нет названия, описания, статуса Арка, чатов,
   приоритета, счётчиков или дополнительных действий. Все связи сразу видны.
7. Строка и полная PR-карточка — два представления одной записи. Выбор любого
   представления открывает одинаковые детали и один и тот же чат PR-карточки.
   Строка не создаёт копию и не считается отдельной задачей в счётчиках доски.
8. В футере полной PR-карточки остаётся ссылка на Арк, как сейчас; рядом с ней
   показывается статус Арка. Это последнее уточнение заменяет размещение
   статуса Арка в теле полной PR-карточки в предыдущих прототипах.
   Футер Task содержит Tracker и Codex; статуса Арка в нём нет.
9. В деталях карточек футер не дублируется. Из деталей PR доступен переход к
   связанной Task и её исходному чату, без подмены собственного чата PR.
10. Одному Арк ПРу соответствует одна постоянная PR-карточка с одним привязанным
    чатом. Новые раунды замечаний используют эту карточку и чат, а не создают
    очередную карточку или новый чат. До первой привязки чат может отсутствовать;
    последующие запуски используют существующую привязку.
11. Родительскую Task пользователь переносит из Review в Done вручную.
    Мерж всех связанных ПРов, завершение чатов и отсутствие связей сами по себе
    не завершают Task.
12. Существующее поведение Telegram approval сохраняется: поллинг переводит
    PR-карточку в TODO уже при создании запроса запуска, до подтверждения.
    TODO включает и ожидание аппрува, и выполнение чата; UI различает эти
    состояния существующим индикатором запроса и индикатором исполнения.
13. Карточки, созданные cron-источниками, имеют отдельный тип `Schedule` и
    остаются на доске. У них не требуется Арк ПР; существующие чаты, история,
    расписания и состояния сохраняются. Источник расписания остаётся Source,
    а созданная им обычная карточка становится Schedule.

## Сценарий работы и навигация

- Пользователь создаёт Task, привязывает тикет и чат разработки. После создания
  ПРа создаёт или выбирает существующую PR-карточку и связывает её с Task.
  Task переводится в Review; такая связь сама по себе не завершает разработку
  и не переносит карточки между колонками.
- PR-карточка в Polling ожидает настроенные события. Inbox означает, что
  требуется внимание пользователя; TODO включает ожидающий Telegram approval
  запрос запуска и выполняющийся чат. Ожидание подтверждения не изображается
  как уже работающий чат.
- После изменения состояния PR его отдельная карточка оказывается в новой
  колонке, а строка под Task показывает то же состояние. Task остаётся в Review.
- Во время запуска доступны как чат PR, так и исходная Task. Завершение запуска
  от поллинга сохраняет существующий возврат TODO → Inbox, только если карточка
  всё ещё принадлежит этому запуску. Ручные запуски сами карточку не двигают.
  Ручной перенос в Polling или другую колонку защищён от позднего возврата.
- Существующее завершение PR-карточки в Done по ручному действию или явно
  настроенному правилу остаётся доступным. Связь не исчезает, строка отражает
  Done. Родительская Task остаётся в Review до ручного переноса пользователем.
- Клик по строке выбирает PR, а не Task. Он не начинает перетаскивание родителя
  и не запускает чат. Для перемещения используется полная карточка.
- Переход к родителю работает, даже если Task скрыта текущим поиском или
  свёрнутой колонкой. Привязка не меняет source, параметры поллинга или чат.

## Статус Арка

Статус нашей карточки и статус Арка независимы. Например, PR-карточка уже может
быть в TODO, пока Арк всё ещё сообщает `Waiting for changes`.

- Футер показывает наблюдавшийся статус самого привязанного ПРа, с обозначениями
  страницы Арка: например, `Waiting for review`, `Waiting for changes`,
  `Waiting for checks`, `Ready to merge`, `Merged`. Состояние карточки, работа
  чата или отдельно зелёные checks не заменяют официальный статус ПРа.
- Статус обновляется и в Inbox / TODO. Чтение метаданных не является запуском
  правил ожидания: вне Polling эти правила по-прежнему не должны запускать
  промпты или двигать карточку.
- До первого успешного чтения показано отсутствие известного статуса.
  При ошибке сохраняется последнее подтверждённое значение с доступным
  признаком неактуальности; если значения ещё нет, показана недоступность.
  Ошибка чтения не означает ни Merged, ни готовность к мерджу.
- После смены привязанного ПРа старый статус не показывается как статус нового.
  Конфликт старого поллинга с новым ПРом должен быть явно обработан при
  проектировании, без тихой перенастройки правил или запуска работы.
- Ссылка на Арк и её статус образуют одну группу футера. На узкой карточке
  допустим перенос группы; оба значения и Codex-контрол остаются доступными.

## Связи и создание

У Task может быть несколько PR-карточек, у связанного PR — одна родительская
Task; PR без привязки к родителю также может существовать отдельно.
Пользователь явно связывает существующие карточки, снимает связь или выбирает
другого родителя. Повтор добавления той же связи не создаёт вторую строку.

Связь разработки отличается от происхождения карточки из Sources. Изменение
родителя не меняет source identity, авторство, дедупликацию событий или frozen
launch requests. Номер Tracker в тексте ПРа может помогать поиску кандидатов,
но не доказывает связь и не должен молча выбирать Task или чужой чат.

Тип учитывается при ручном создании и в шаблонах создаваемых Sources карточек.
Сохранение новой PR-карточки требует валидного Арк PR ID / URL. Добавление чата
само по себе не делает карточку PR. Повторное обнаружение того же ПРа, включая
обнаружение другим Source или после перезапуска, обращается к существующей
PR-карточке. Идентичность определяется Арк ПРом, а не названием, номером раунда,
чатом или источником. Само обнаружение не заменяет чат и не является разрешением
повторно запускать работу; сохраняется дедупликация событий и запусков.

## Сохранность и эксплуатация

- Новая версия сохраняет существующие ID, названия, описания, приоритеты,
  чаты, историю, Done-даты, настройки, курсоры, source-связи и запуски.
- Старые обычные карточки, созданные PR review / PR feedback автоматикой либо
  имеющие значок просмотра / комментариев, классифицируются как PR. Пользователь
  разрешил убрать у таких карточек привязку Tracker. Значок устанавливается по
  действующему признаку происхождения; одного совпадения названия недостаточно.
- Cron-карточки — согласованное исключение из правила об автоматике: это Schedule.
  Сами Sources не превращаются ни в PR, ни в Schedule.
- Ручные карточки разработки с одновременно указанными Tracker и PR сохраняются
  как Task. При миграции прежняя прямая PR-ссылка сохраняется событием в History,
  а активная PR-привязка очищается независимо от ручного связывания. Отдельная
  PR-карточка сохраняется без автоматически установленного родителя; предложения
  пар остаются в частной карте для ручного связывания. Это правило подтверждено
  пользователем 2026-11-11. Если отдельной PR-карточки нет, миграция её не создаёт.
  ID, чат, Tracker, история и колонка Task сохраняются. Создание PR-карточки
  остаётся отдельным явным действием; исходный чат Task не переносится.
- Совпадение PR URL у Task разработки и PR-карточки не требует слияния:
  карточки сохраняют разные роли, ID, чаты и историю. Несколько настоящих
  PR-карточек одного ПРа с разными чатами нельзя молча объединять.
- Конкретная карта перехода является снимком для проверки и сама ничего не
  применяет. Перед будущим применением перечитываются карточки и их версии;
  изменения после снимка не перезаписываются старым планом.
- Конфликт или ошибка сохранения связи / состояния не оставляет строку и
  полную карточку с разными подтверждёнными состояниями. Повтор операции
  безопасен; сохранённые связи переживают перезапуск.
- Чтение доски остаётся компактным: строки связей и статус Арка не требуют
  загрузки полных настроек, истории чатов или отдельного detail-запроса на
  каждую строку. Одновременный показ строки и карточки не удваивает опрос ПРа.
- Клавиатурой доступны строки, переходы и контролы. На узкой карточке номер
  ПРа и состояние нашей карточки остаются в одной строке без обрезания смысла.
- Палитра, Sources, motion, селекты, Done-хронология и настройки запусков
  сохраняют действующее поведение, кроме отдельно согласованных изменений.

## Проверяемые результаты

1. Привязка чата к Task оставляет подпись TASK; PR с чатом и без него имеет
   подпись PR. В футере Task нет Add PR, в футере PR нет Add ticket.
2. У Task в Review связаны три PR-карточки из Polling / TODO / Inbox. Под
   футером ровно три однострочные ссылки, состоящие из номера ПРа и состояния.
   Все три полные PR-карточки одновременно доступны в своих колонках.
3. Клик по строке и по полной карточке одного PR открывает один ID и один чат.
   Переход к исходной Task открывает её ID и её чат без изменения привязок.
4. Перенос PR из Inbox в TODO обновляет строку; Task остаётся в Review.
   Ошибка переноса восстанавливает согласованное отображение обоих представлений.
5. В футере PR рядом с ссылкой отображается `Waiting for changes`, пока
   карточка находится в TODO. Новое наблюдение меняет статус Арка независимо
   от положения карточки, без запуска правил вне Polling.
6. Ошибка Арка сохраняет последнее значение с признаком неактуальности.
   До первого чтения нет выдуманного статуса. Перезапуск не создаёт вторую
   связь, не перезапускает чат и не передвигает Task из Review.
7. Снятие связи убирает только строку. Полная PR-карточка, её чат и история
   сохраняются. Добавление связи не создаёт ещё одну полную карточку.
8. Поиск по PR ID / URL продолжает находить PR-карточку, по Tracker ID / URL —
   Task. Связанные строки видны вместе с найденной Task, даже если отдельный
   PR не совпал с запросом. Счётчики считают записи, а не их представления.
9. Второй раунд замечаний к тому же ПРу использует прежний ID PR-карточки
   и прежний чат. Повторное discovery и перезапуск не создают дубликат.
10. Мерж всех связанных ПРов обновляет их статусы Арка и сохраняет Task в Review.
    Только ручной перенос Task завершает её и устанавливает её дату входа в Done.
11. При создании polling-запроса с Telegram approval карточка уже в TODO,
    показано ожидание аппрува. После подтверждённого запуска состояние остаётся
    TODO, а индикатор меняется на выполнение чата. Само ожидание аппрува
    не создаёт новый чат и не изображается как выполнение.
12. Старая карточка с происхождением PR review / PR feedback становится PR,
    её Tracker-привязка может быть очищена без переноса или замены её чата.
    Cron-карточка становится Schedule, остаётся на доске и сохраняет историю.
13. После ручного связывания исходной Task и существующего PR обе записи,
    оба чата, история, состояния и даты Done сохранены. Источник PR-карточки
    и родительская Task остаются разными связями.
14. Явное решение отвязать ПР у старой ручной Task очищает только прямую
    PR-привязку. Новая PR-карточка и новый чат не создаются, существующий
    чат и состояние Task сохраняются. Прежний PR ID / URL доступен в History
    уже до ручного связывания. Повтор миграции не дублирует событие отвязки.

## Применение карты старых карточек

Ручная кардинальность связей и тип Schedule подтверждены. Предложения конкретных
пар не являются автоматически установленными связями. Классификация старых
карточек в частной карте согласована; для отдельно уточнённой ручной Task
выбрано отвязывание ПРа без создания PR-карточки. Старые прямые PR-ссылки Task
сохраняются в History и очищаются из активного поля; связи устанавливаются вручную.
Продуктовых вопросов по переходу старых карточек не осталось. Применение карты — отдельный
этап, с проверкой актуальных версий. Правило «один ПР — одна PR-карточка» не
разрешает объединять чат разработки с чатом исправлений.

Напоминания по сроку ожидания ревью, автоматические пинги людям и управление
несколькими чатами одной карточки в этой спецификации не согласованы.
Она делает ожидание и связи видимыми, но не задаёт сроки уведомлений.

## Проверенное исходное состояние

На момент подготовки:

- `internal/model/tasks.go` содержит общую карточку без явного типа и четыре
  колонки; `ui/src/App.tsx` вычисляет CHAT / TASK по `thread_id`.
- `source_task_id` означает создавший карточку Source. Это не родительская
  задача разработки. `store_task_outcomes.go` использует source key для
  повторного обнаружения уже созданной карточки.
- `internal/arcanumreview/snapshot.go` уже получает lifecycle `status` и
  `common_status`; компактная проекция карточки пока не содержит статус Арка.
- `internal/polling/runner.go` и ADR-035 связывают активность правил с Polling.
  Отдельное отображение статуса не должно обходить этот запрет на действия.
- ADR-035 и `store_task_completion.go` фиксируют точный ownership возврата
  polling-запуска TODO → Inbox; ручной перенос отказывается от такого возврата.
- `store_task_cards.go` читает компактную доску ограниченным количеством
  запросов, без snapshot JSON и frozen payloads. Это свойство следует сохранить.

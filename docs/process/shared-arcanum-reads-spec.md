# Общие чтения Арканума для Sources, ожиданий и статусов

Дата: 2026-11-12, уточнение объёма 2026-11-13. Исследование и план первого
раунда подготовлены. По уточнению пользователя подтверждённые Merged больше
не опрашиваются; перечисленные статусные сценарии используют подходящий search.
Последнее уточнение заменяет прежние интервалы: search раз в 30 секунд,
comments/checks не чаще раза в 5 минут на PR, fallback get — в 10 минут на PR.
План: `shared-arcanum-reads-plan.md`. Реализация выполнена; актуальные контракты закреплены в ADR-035 и local-task-board-api.md.

## Цель

Сократить повторные чтения одних данных Арка и быстрее доставлять полученные
изменения потребителям. UI, Sources и правила задач используют общий результат
получения фактов, сохраняя независимые условия, курсоры и действия.

## Подтверждённые решения пользователя

- Убрать зависимость получения данных от видимости страницы, сворачивания,
  количества вкладок и фокуса. Общий источник работает постоянно.
- Убрать отдельное принудительное обновление при возвращении на страницу.
  UI показывает текущие общие данные и получает последующие изменения.
- Цель экономии — устранение повторных чтений и получение нескольких полезных
  фактов из одного ответа. Скрытие страницы больше не служит способом экономии.
- Подтверждённый Merged — терминальный факт: ради него больше не выполняются
  периодические get/search/comments/checks, в том числе после restart и открытия UI.
- Частый общий search снабжает данными и будит Sources/правила и обновляет
  футеры; отдельные сетевые обходы этих потребителей устраняются. Comments,
  checks и get имеют независимые общие ограничения 5/5/10 минут.
- Статус футера, PR merged, Request changes, New commit и обнаружение PR для
  ревью получают необходимые факты из подходящего pr search. Предварительный
  get не является обязательным шагом этих сценариев.

Это заменяет соответствующие требования `pr-footer-visibility-spec.md`.
Не вводится новый настраиваемый пользователем Source или отдельный экран.

## Что подтверждено по текущему коду и API

Проверен код на коммите `a780743` и установленный Arcanum CLI.

| Потребитель сейчас | Чтения одного невмерженного PR |
|---|---|
| Футер | `pr get` и поиск списка PR его автора |
| Ожидание событий | Те же два чтения и комментарии; для условия checks — ещё страницы checks |
| Source | Сначала список кандидатов; затем для каждого кандидата повторяется полный snapshot, при необходимости checks |

- Один авторский поиск уже возвращает данные нескольких PR, но сейчас
  результат выбирается для одного PR, остальные записи не переиспользуются.
- `ReadPRSnapshot` всегда читает комментарии невмерженного PR, в том числе
  когда настроенному условию нужны только статус или опубликованный head.
- Кеш `rulePRClient` работает только внутри одной проверки одной задачи.
  Между задачами, Sources и metadata worker общих наблюдений нет, хотя в main
  им передан один экземпляр CLIClient.
- Подтверждённые Merged тоже участвуют в периодическом обновлении футеров.
- Worker футеров имеет двухсекундную паузу после каждого PR. Рабочий runner
  последовательно обрабатывает до 20 задач; Source рассматривает до пяти
  новых кандидатов за проход. Дублирующий IO увеличивает задержку очередей.
- Live-поиск по автору подтвердил наличие `common_status`, `full_status`,
  `active_diff_set`, `diff_sets` в одном списочном ответе. Это не один и тот же
  контракт с полями v2 `pr get`: их смысл нужно явно сопоставить.
- Проверенный синтаксис поиска `id(id1,id2)` сервер отверг с HTTP 400.
  Возможность получить произвольные известные PR одной ID-выборкой не доказана.
- В проверенных ответах CLI не было `total_count`; итог `--all` содержал
  `has_next:false`. Полнота списка на нескольких страницах этими небольшими
  пробами не доказана. До реализации пакетной обработки нужна проверка
  пагинации на неизменном наборе, заведомо большем размера страницы.

Уточнение 2026-11-13: явные страницы limit=1/offset=0,1 совпали с limit=2;
ответы содержали total_count=2. При --all/limit=1 CLI вернул только одну запись.
Проверка его реализации показала, что --all использует только has_next и
не переносит total_count. План первого раунда предусматривает явную пагинацию.

Число вызовов CLI не равно гарантированному числу HTTP-запросов: пагинация
и retry могут увеличить последнее. Измерения реального HTTP-трафика не проведены.

## Какие чтения нужны

| Семейство | Назначение и границы |
|---|---|
| `pr search` | Обнаружение PR по условиям Sources; совместное получение статусов, авторов, заголовков и опубликованных ревизий для нескольких PR |
| `pr get` | Только исключительный fallback для недостаточной/отсутствующей строки search или неизвестной идентичности; не обязательный шаг статусного пути |
| `pr comments` | Условия об ответах/закрытии замечаний и необходимая исходная фиксация замечаний для создаваемого или перевзводимого ожидания |
| `diff checks` | Состояние обязательных checks конкретной опубликованной ревизии для правил, которым эти checks нужны |

Для футера не нужны комментарии и checks. Для одного события PR merged не нужны
комментарии. Запрос конкретного PR не требуется повторять, если подходящий
общий ответ уже содержит все необходимые достоверные факты нужной свежести.

## Соответствие UI и необходимых фактов

Это минимальные потребности элементов UI и их поведения, а не описание
нынешнего избыточного состава `ReadPRSnapshot`.

| Часть интерфейса | Нужные данные Арка |
|---|---|
| Arc status рядом с #PR в футере полной PR-карточки | Подходящий pr search: full_status/common_status; без обязательного get/comments/checks |
| Ссылка #PR в футере | Хранится локально; само отображение не требует чтения Арка |
| Строка связанного PR под Task: #PR + Inbox/TODO/Polling/Done | Только наши локальные связь и колонка; статуса Арка в строке нет |
| Pollers Active/Paused, подписи условий, Cron in N min | Локальная конфигурация, колонка и расчёт расписания; отображение не читает Арк |
| Polling: Last attempt/success/error, Next check | Сохранённый результат нашего поллинга; открытие диагностики не повторяет проверку |
| Polling: PR merged | Положительная строка pr search с full_status/common_status=merged; после подтверждения локальный терминальный факт |
| Polling: Request changes | common_status и lifecycle из подходящего pr search, без get/comments/checks |
| Polling: New commit | Head опубликованной ревизии и её идентичность из подходящего pr search, без get/comments/checks |
| Polling: All answered / All resolved | Опубликованные замечания/ответы из `pr comments` и локальный курсор отслеживаемых замечаний |
| Polling: Failed merge checks | Идентичность опубликованной ревизии и `diff checks`; Approved и Closed issues исключаются |
| Source PR review | Подходящий pr search для обнаружения PR, ожидающих ревью заданного пользователя; baseline дочерних comment-условий отдельный |
| Source PR feedback | Список авторских PR со статусами; checks опубликованных ревизий, если выбрано соответствующее событие; baseline будущего ожидания |
| Source Schedule и Cron-правила | Запросы Арка не нужны |
| Overview, History, приоритет, наши колонки и типы, счётчики, поиск, фильтр, связи Task/PR | Локальные данные; переходы и редактирование могут обращаться к нашему API/App Server, но сами по себе не читают Арк |
| Иконка чата и Running/Completed | Codex App Server, не Арк |

Начальная фиксация замечаний требуется только если будущие/текущие условия
действительно отслеживают ответы или закрытие замечаний. Старый Tracked сам по
себе не должен заставлять search-only правило читать comments. При добавлении
comment-условий выполняется свежая инициализация с прежней защитой от дублей. Клик внешней ссылки
открывает сайт Арканума с его собственными запросами; это не фоновый трафик демона.

## Требования к общему получению данных

1. Объединять совпадающие потребности в чтении одного PR/списка/ревизии.
   Добавление футера или ещё одного правила не создаёт копию уже выполняемого
   чтения тех же фактов. Результаты доступны всем заинтересованным потребителям.
2. Использовать полезные данные всех записей списочного ответа. Не повторять
   один авторский поиск для каждой подходящей карточки того же автора.
   Разные критерии обнаружения PR нельзя заменять одним списком без доказанной
   полноты: например, список известных авторов не заменяет Source новых ревью.
3. Получать комментарии/checks только там, где они нужны текущему правилу
   или его корректной инициализации. Смена head или common_status не является
   единственным поводом их читать: ответы могут появиться без нового коммита,
   checks могут измениться на том же опубликованном diff.
4. Любое свежее подходящее наблюдение рабочего поллинга доступно проекции
   статуса. Футер не должен ждать своего прежнего пятиминутного обхода после
   того, как нужный статус уже получен другим потребителем.
5. У каждого результата известны время получения, идентичность PR/ревизии,
   состав полученных фактов и успешность. Старое или неполное значение нельзя
   выдавать за новое полное наблюдение. Поздний ответ не затирает более новое.
6. Интервалы и здоровье разных потребителей остаются различимыми. Получение
   статуса само по себе не подтверждает успешность проверки комментариев или
   checks; ошибка одного вида данных не обнуляет хорошие данные другого.
7. Ошибка/429/тайм-аут не означают отсутствие замечаний, успех checks или Merged.
   Сохранять последнее успешное значение с действующим обозначением проблемы.
   Повтор общего сбойного запроса не размножается по количеству потребителей.
8. Полнота страниц обязательна там, где вывод зависит от отсутствия записи.
   PR, отсутствующий в неполной, отфильтрованной или открытой выборке, нельзя
   автоматически считать вмерженным. При необходимости получить его состояние
   точечно. Ошибка одной группы не должна блокировать независимые группы.
9. AND/OR правила используют факты одного согласованного логического опроса,
   а не накопленные совпадения разных раундов. Mixed AND ждёт общего
   разрешённого чтения медленных ресурсов; старый cached failure не соединяется
   с новым Request changes. Статусная OR-ветвь не ждёт comments/checks. Checks относятся к выбранному
   опубликованному diff; черновая ревизия не подменяет опубликованную.
   Атомарный снимок Арка для всех ресурсов не обещается: текущий API читает
   их отдельными операциями.
10. Общими являются наблюдения, а не курсоры или право выполнить действие.
    Сохранить независимые курсоры задач/правил/Sources, дедупликацию событий,
    generation-проверки при принятии результата, приоритет Done и существующие
    правила запуска/Telegram approval/возврата TODO → Inbox. Пассивная карточка
    вне Polling не получает право запускать правила от нового общего статуса.
11. План реализации должен обосновать достаточный объём хранения и запросов:
    не выгружать бесконечную историю всех PR автора каждую минуту ради нескольких
    карточек. Общий источник не должен замедлять ручные операции доски.

## Периодичность и объём первого раунда

Уточнение пользователя заменяет сохранение прежних сетевых интервалов и
пятиминутный metadata fallback. Единый collector получает данные независимо
от страницы; поллеры и UI используют полученные общие наблюдения.

| Ресурс | Частота начала чтения | Область общего ограничения |
|---|---|---|
| pr search | Каждые 30 секунд при наличии потребителей | Один обход на точный общий query, все его страницы |
| pr comments | Не чаще раза в 5 минут, только при необходимости | PR ID, все потребители/правила вместе |
| diff checks | Не чаще раза в 5 минут, только при необходимости | PR ID, даже при смене published diff |
| pr get | Только fallback, не чаще раза в 10 минут | PR ID; регулярного обхода нет |
| Done / подтверждённый Merged | Ноль чтений специально ради них | Независимый активный спрос учитывается отдельно |

Первое нужное чтение допускается сразу при отсутствии действующего cooldown.
Следующие сроки общие и сохраняются после restart, rearm, смены head/правила,
добавления карточки и UI refresh. Если свежий baseline ещё нельзя прочитать,
правило ждёт разрешённого срока без продвижения курсора. PR interval_seconds
не управляет сетью поверх этих ограничений. Оба редактора PR показывают
фактические интервалы только для чтения и поддерживают сохранённые конфиги.
Для /pollers и общего восстановления учитывать ожидаемый срок нужного ресурса,
просрочку и терминальный PR без будущего чтения. Cron сохраняет своё расписание.
Нужные comments/checks одного PR читаются в общем медленном раунде раз в
5 минут; добавление нового ресурса ждёт ближайшего общего срока. Ненужные
ресурсы не читаются. Это сохраняет совместную проверку AND без двух
несовпадающих независимых циклов на одном PR.
Одно новое search-наблюдение сразу обновляет футеры и будит заинтересованные
правила/Sources без повторного IO. Медленные ресурсы будят свои условия после
собственного чтения; сеть не выполняется внутри проверки потребителя.

При single-attempt CLI ошибки не обходят интервалы через скрытые retry.
Retry-After может увеличить паузу; разные страницы считаются отдельными
вызовами одного обхода. После получения слота исполнителя перед отправкой
первой страницы каждого метода сохраняется его собственный срок. Следующий
совместный раунд PR ждёт наиболее позднего срока comments/checks, включая
перезапуск. При старте comments в 00:00 и checks в 00:40 он возможен с 05:40. Ошибка записи срока откладывает запуск команды.
Ожидаемые задержки: до 30 секунд для search-фактов и до 5 минут для
comments/checks плюс IO/очередь. Fallback может задержать уточнение до 10 минут.
Промежуточное состояние, целиком пропущенное периодом, не гарантируется.

Число поисков зависит от разных нужных query и страниц, а не от числа карточек.
Для одностраничных ответов среднее: 2 × Q + C/5 + K/5 + G/10 команд в минуту
после первоначальной загрузки. Q — общие search query, C/K — PR с нужными
comments/checks, G — PR с продолжающейся необходимостью get. При достаточном
search G=0. Пять PR одного автора только со статусами могут обходиться двумя
командами в минуту суммарно; с comments и checks для каждого — четырьмя.
Разный assignee discovery query и дополнительные страницы увеличивают число.

Уточнение пользователя 2026-11-13: Done исключается из регулярного
`GET /v1/task-cards` и SSE reconciliation полной компактной проекции.
Done загружается отдельно по Show Done (`?column=done`) из локальной БД;
таймер, focus, invalidate и reconnect не перечитывают этот набор. Точечное
открытие по ID, связи Task/PR, перемещения и редактирование сохраняются.
Выбранный Done-detail также читается по явному действию, без автоматического
refetch по общим таймерам/событиям; ответы собственных команд обновляют его.
Обычные списки не получают полные Done DTO или их request summaries;
краткие локальные ссылки на связанные Done допустимы без загрузки архива.
Фоновая регистрация health получает компактный список активных поллеров
и отключает выбывшие ID. С закрытой доской регистрация обходится без полного
ListTasks и поштучного чтения истории и snapshots Done-карточек.

Done PR-карточка также не создаёт фонового спроса на Арк, независимо от её
реального lifecycle. Фильтр применяется в metadata schedule до LIMIT; перенос
в Done проверяется перед новым IO. Начатый запрос может завершиться, но не
возобновляет расписание Done-футера. Show Done и detail read не запускают Арк.
Если тот же PR нужен активному правилу/Source или другой карточке вне Done,
независимое чтение продолжается. Done не доказывает Merged и не очищает кеш.
Reopen возвращает невмерженный PR в общий search, сохраняя cooldown редких чтений;
подтверждённый Merged сохраняет отдельное терминальное ограничение.

Подтверждённый Merged исключается из due-набора и не опрашивается снова.
Последнее подтверждение хранится в существующем metadata cache и загружается
до запуска readers после restart. Такой статус не становится stale только
из-за возраста. Ошибка старого запроса или запоздалая open-строка его не отменяет.
Done нашей карточки не доказывает Merged; Discarded не считается Merged.
Правило распространяется и на PR, указанный только в правиле Task/Schedule,
без самостоятельной PR-карточки: терминальный факт хранится по PR ID.

Под «не опрашивается» понимается отсутствие запросов и страниц, запланированных
ради этого терминального PR. Его случайное присутствие в общем ответе поиска,
выполненного ради других PR, не требует дополнительной фильтрации сервера.
Если у задачи нет правила PR merged → Done, терминальный факт не даёт права
самовольно её переместить; правила используют этот факт без сетевых повторов.
Остальные условия терминального PR не требуют comments/checks и не блокируют
правила других PR из-за отсутствия этих ресурсов.

Прежнее предложение минутного режима и сохранение сетевых interval_seconds
заменены указанным расписанием по последнему уточнению пользователя.

## Как принять результат

- Обычный `/v1/task-cards` и SSE не загружают полные Done-карточки и их request
  summaries; Show Done выполняет отдельное локальное чтение без последующего
  фонового обновления набора. Deep links, связи с Done и переносы/reopen
  сохраняются, поздняя загрузка не откатывает новые версии/колонки.
- Единственная PR-карточка в Done не вызывает Arc IO после restart, открытия
  Done или detail read; она не занимает due batch. Перенос до IO снимает её
  спрос, reopen восстанавливает его по свежести. Другой активный потребитель
  того же PR продолжает работать; Done не трактуется как Merged.
- В сценарии нескольких PR одного автора общий статусный ответ не запрашивается
  заново для каждой карточки, Sources и ожидающих правил. Совпадающие чтения
  комментариев одного PR и checks одной ревизии также не дублируются в раунде.
- Пять PR одного автора в подходящем одностраничном search: не более одного
  общего обхода в 30 секунд, без обязательных get/comments/checks для статусных
  сценариев. Нужные comments/checks ограничены 5 минутами на PR, get — 10.
  Новый diff, rearm, повторный потребитель и restart не обходят ограничения.
- При mixed AND не использовать старый медленный факт вместе с новым статусом;
  дождаться общего разрешённого раунда. Статусные OR-ветви продолжают работу.
  В Runner + SQLite проверить готовую OR-ветвь при ожидании и при ошибке
  другой ветви, в том числе со старым будущим NextCheckAt. Событие принимается
  один раз. Курсор и Matches ожидающей/ошибочной группы сохраняются.
  Ожидание baseline не продвигает курсор и не считается попыткой Арка.
- Записать сравнимые показатели до/после: реальные страницы/попытки запросов,
  успешность, длительность обновления, возраст данных и очередь потребителей.
  Для пяти открытых PR одного автора с одностраничными ответами и только
  футерами ожидаются 10 команд за пять минут в обоих вариантах. Новый режим
  обновляет всю пятёрку одним search каждые 30 секунд. Критерии приёмки —
  частота наблюдений, число команд на общую выборку, отсутствие дублей
  и задержка доставки фактов правилам и карточкам. Считать отдельно
  страницы поиска, комментарии, checks, get и retry.
  Основной сравнительный сценарий — долго открытая доска с теми же правилами
  и карточками. Постоянная работа при закрытой доске — согласованное изменение;
  её дополнительный трафик учитывать отдельно, не обещая уменьшение запросов
  относительно прежней паузы в каждом возможном режиме.
- Новое замечание без смены head и состояние checks того же diff
  обнаруживаются очередным разрешённым чтением; промежуточные состояния
  между чтениями не гарантируются; отсутствие PR на первой странице не создаёт ложный Merged.
- Одновременные потребители не создают повторный запуск Codex или новую
  PR-карточку. Ошибки, смена конфигурации во время IO и перезапуск сохраняют
  существующую защиту от устаревших результатов и дублей событий.
- Закрытие/открытие/возвращение браузера не меняет расписание запросов в Арк.
  Несколько окон не умножают трафик. Открытие показывает текущие общие данные.

## Границы и оставшиеся решения

Сохраняются типы карточек, статусы Арка, условия событий, правила действий,
показ Done по запросу и связи. Меняется загрузка Done и его участие в фоне;
новый экран не нужен. Не вводятся webhook, внешняя очередь, отдельный
сервис или полный архив PR. Новая схема БД не является требованием этой спеки.

Первый раунд уже включает исключение Done из регулярного чтения доски и
фонового спроса на Арк, прекращение чтений подтверждённых Merged и search-first
путь перечисленных сценариев. Его план закрывает полноту страниц, нормализацию
full_status/common_status/публикации, безопасный fallback и изменение baseline
без скрытых comments, общее расписание 30 секунд / 5 минут / 10 минут и
отсутствие обхода лимитов через потребителей, смену diff, retry или restart.


Уточнение API 2026-11-13: pr search с author(example) и common_status(merged)
на реальных данных вернул положительные merged строки с full_status=merged,
common_status=merged, status=published, автором и данными ревизий. Точечный get
одной записи подтвердил merged. Поэтому status=published нельзя трактовать
как lifecycle=open, а Merged можно определять из положительного search-ответа.
Идентификаторы проверенных реальных PR в публичный документ не включены.

# План: best-effort Sync и восстановление через off/on

Статус: закоммичено и установлено локально, 2026-11-07; события и поздняя очистка
проверены в Telegram, полная UI-приёмка off/on предстоит.
Результаты и ограничения: [проверка реализации](sync-best-effort-recovery-validation.md).
Основание: [согласованная спецификация](sync-best-effort-recovery-spec.md).

## Решение

Оставить HTTP Bot API, обычные названия и существующие SQLite, egress governor,
delivery queue, writer manager и cleanup loop. Добавить журнал создания топиков
и приём событий создания. Неизвестный результат блокирует только повтор той же
операции. Выключение закрывает Telegram-маршруты и запускает очистку, а наблюдение
за уже начатой работой Codex продолжается независимо от состояния Sync.

Название используется только для восстановления операции создания. После
подтверждения маршрутизация остаётся по сохранённым topic ID и thread ID.
Пул топиков, технические метки, MTProto, автоматическое удаление спорных дублей
и интерфейс ручного выбора привязки не входят в план.

## Что меняется в существующей системе

| Сейчас | Изменение |
| --- | --- |
| `sync.go`: один `sync.topic_create.<session>` останавливает discovery ещё до `thread/list` | Независимые операции создания; обход пропускает проблемную цель и продолжает остальные |
| `sync_new_task.go`, `external_dispatch.go` создают топики отдельными путями | Все три пути используют один контракт сохранения и подтверждения операции |
| `telegram/bot.go`: offset продвигается до handler; пустое служебное сообщение отбрасывается | Событие создания проверяется и сохраняется до продвижения offset |
| `deactivateSync` отказывает при незавершённой работе; force вызывает interrupt | Обе формы переводят отображение в off без interrupt и без ожидания завершения хода |
| Cleanup удаляет строки topics/drafts; reconciliation ориентирован на текущую сессию | Незавершённая работа сохраняется и сверяется во всех сессиях после удаления топика |
| `health.go` отдельно сохраняет эпизод и ставит сообщение в очередь, игнорируя некоторые ошибки | Для новых случаев состояние и уведомление фиксируются атомарно в существующей delivery queue |

Действующие контракты: ADR-032/033/034, ADR-026 для общего App Server,
`docs/research/contract-matrix.md`, `docs/testing/regression-map.md`.
Семантика общей паузы и старого drain будет явно заменена в этих документах.

## 1. Операции создания и события

Добавить специализированные таблицы, без универсальной очереди задач:

- `sync_topic_creations`: ID операции, bot/group, Sync session, вид и ключ цели
  (thread, draft intent или external request), номер попытки отображения,
  неизменное отправленное название, данные для материализации draft, состояние,
  известный topic ID, диагностический исход и время. Индекс поиска по bot/group/name.
- `sync_topic_created_events`: bot/group/topic ID, update ID, автор, точное имя,
  ID сопоставленной операции либо причина отсутствия сопоставления. Повтор события
  идемпотентен; запись не содержит произвольного пользовательского текста.

Жизненный цикл операции: `prepared → sending → confirmed | unknown | failed`.
`unknown → confirmed` разрешён по позднему ответу или однозначному событию.
Неоднозначность хранится как причина у незавершённой операции/события, а не как
новый глобальный режим. Признак закрытой сессии определяет cleanup вместо привязки.

Одна логическая цель не получает вторую незавершённую операцию в той же сессии.
После штатного удаления подтверждённого топика по неактивности новое появление
чата может получить следующую операцию отображения. Это не разрешает повтор
`unknown`. Для `/newchat` ключом служит входное сообщение или callback intent;
для внешнего запуска — request ID. Повтор доставки команды не создаёт новый intent.

Перед внешним вызовом сохранять `sending`; после crash эта запись становится
`unknown`, даже если запрос фактически не успел уйти. Это допустимый ложный
пропуск вместо риска повторного создания. `prepared`, для которого вызов точно
не начинался, можно продолжить только в действующей сессии.

Запросы проходят существующий governor. Подтверждённый `429` допускает повтор
после cooldown; для external launch остаётся существующий явный Retry.
Тайм-аут, EOF, неполный успешный ответ и сомнительный серверный исход считаются
`unknown`, а не доказательством отсутствия топика. Окончательный отказ сохраняется
с диагностикой; бесконечный повтор постоянной ошибки каждый цикл не нужен.
На этапе реализации проверить текущую классификацию `APIError`/`IsRetryable`:
не всякая ошибка HTTP доказывает отсутствие побочного эффекта.

Ответ `createForumTopic` подтверждает свою операцию напрямую. Подтверждение,
создание binding/draft и изменение её состояния выполняются одной транзакцией.
После ошибки SQLite не удалять топик немедленно в качестве компенсации:
сохранённая операция и событие дают возможность завершить запись позднее.

### Сопоставление события

1. В Bot adapter принять только `message.forum_topic_created` из настроенной
   группы от собственного bot ID, полученного через `getMe`, с валидным topic ID.
   Проверка выполняется до SQLite. Это отдельный служебный вход, не расширение
   допуска пользовательских сообщений и callbacks.
2. Сохранить событие. Сначала проверить уже известный topic ID: это повтор
   подтверждения, а не поиск другой цели с таким же именем.
3. Для неизвестного ID сопоставить точное отправленное название с операциями
   всех путей и сессий. Подтверждённая операция с другим ID не является свободной
   целью; историческая неизвестная операция остаётся возможным кандидатом.
   Нельзя выбирать по текущему названию Codex, рангу, свежести или «первой строке».
4. Привязывать только взаимно однозначную пару среди сохранённых кандидатов.
   При нескольких операциях или топиках оставить их непривязанными и уведомить
   Control. Поздний прямой ответ может снять неоднозначность. Уже подтверждённую
   привязку другой кандидат не заменяет.
5. Подтверждение операции закрытой сессии не создаёт активную привязку:
   известный ей топик направляется в cleanup. Неоднозначный кандидат не удаляется.

Исторические записи подтверждений сохраняются и после удаления topic binding.
Старые неизвестные операции не забываются по таймеру: иначе позднее событие
можно ошибочно присвоить новой операции с тем же названием. Архивация с сохранением
минимальных полей допустима позже; отдельный retention-проект сейчас не нужен.
Имя не обеспечивает exactly-once и не позволяет обнаружить все дубли — это
согласованное ограничение best effort.

### Приём обновлений

В `Bot.Run` перед бизнес-обработкой batch сохранять прошедшие admission события
создания. При ошибке записи не передвигать offset за несохранённое событие и
не переходить к следующему batch; повторять сохранение с задержкой. После
успешной записи сопоставление можно повторять независимо от Telegram polling.
Callback acknowledgement остаётся в существующей критической полосе.

Не превращать ошибку отправки ответа пользователю в повтор исполнения команды.
Для prompt/steer/драфтов сохраняется существующая защита receipts; для новых
create intents добавляется такой же стабильный ключ. Сообщение, полученное
в непривязанном топике, отклоняется окончательно, даже если привязка появится позже.
Для этого фиксировать отказ по message ID до побочных эффектов и ответа.

## 2. Выключение отображения без остановки Codex

Выбран минимальный вариант: оставить execution-поля в существующих topics/drafts,
но перестать удалять содержащую их строку вместе с Telegram-топиком.
Отдельная таблица исполнений потребовала бы переноса всех start/steer/recovery
путей и двухэтапной миграции без необходимого выигрыша для этой задачи.

Для topics добавить состояние отображения `deleted`. Для drafts отделить
`telegram_state` (`connected/cleanup/deleted`) от состояния запуска: сейчас
`MarkSyncOff` затирает `starting/unknown` значением `cleanup`.
При удалённом топике незавершённые поля запуска, generation, receipt и известные
thread/turn IDs сохраняются. После подтверждённого терминального исхода строку
можно удалить; receipts и журнал создания остаются для дедупликации.

Выделить в daemon небольшой общий путь сверки принадлежащей ему работы,
использующий прежний writer manager. Его вход — все незавершённые rows и leases,
включая старые сессии и drafts без известного thread ID. Он не требует active Sync,
доступного Telegram или живого topic binding. Сначала сохраняется авторитетный
результат Codex, затем освобождается lease; доставка в Telegram — отдельная ветка.
Terminal event и периодический read должны приводить к одному результату.

`sync off` выполняет короткий переход состояния:

1. В транзакции установить off, закрыть текущую сессию для новых dispatch/create,
   погасить её callback routes, отметить известные управляемые топики и drafts
   для cleanup; сохранить незавершённую работу и сведения о ранее принятых командах.
2. Прекратить новые отправки из топиков. Принятое, но гарантированно не отправленное
   действие завершить как отклонённое; не откладывать его до следующего on.
3. Запустить существующую асинхронную очистку и дать Control результат перехода.
   Ошибка удаления не откатывает off. Control и Requests исключить из targets явно.
4. Сохранить writer connection/process и нужные подписки до терминального исхода.
   Не вызывать interrupt, ForceClose или автоматический ответ на server request.
   `--force` становится совместимым alias; `/stop` сохраняет явную семантику отмены.

Отсутствие топика не является доказательством завершения работы. Unknown без
достаточных данных остаётся unknown и отражается в Control. Повторный on не
должен обходить его защиту через создание нового binding к тому же thread.

Для thread ID искать владельца среди всех незавершённых записей/leases, а не
только в текущей Sync session. Новый топик показывает текущий snapshot; его новый
ввод проверяет существующее владение и авторитетный turn. Старые кнопки не оживают.
Новые кнопки допустимы только для актуального server request и новой проверенной
привязки; старые request routes не копируются автоматически.

### Конкурентные операции

Не держать `syncMu` на протяжении создания топиков и ожидания start/steer RPC:
под блокировкой подготовить durable intent/receipt и ownership, выполнить IO
снаружи, затем подтвердить результат по исходным session/operation/generation.
Это точечная переделка затронутых путей, а не переписывание всех delivery loops.

Off и начало отправки упорядочиваются коротким общим dispatch gate: для App
Server он защищает проверку состояния и запись RPC frame, но не ожидание ответа.
Для этого в client отделить отправку от ожидания результата без изменения
wire-протокола. Проверка до постановки в goroutine недостаточна. Для Telegram
create повторно проверять session непосредственно в callback governor перед
raw attempt: накопленная очередь не разрешает создание после off.
Уже начавшийся вызов дорабатывает с прежним bounded timeout и независимым от
отображения context. Поздний результат сохраняет execution, но не возрождает
топик. В цепочке `thread/start → turn/start` после off не начинать ещё не отправленный
`turn/start`; успешно созданный пустой чат остаётся в Codex. Уже отправленный
`turn/start` не отменять и не повторять.

Polling не должен ждать завершения долгой команды, иначе off из Telegram не
попадёт в этот путь. `/sync on` и создание drafts ставят durable intent и будят
существующий reconcile; start/steer после durable claim выполняются отслеживаемой
runtime-задачей с результатом через текущий delivery/Control путь. Число задач
ограничивается ownership: один dispatch на цель, существующий лимит создания
за проход. Не запускать произвольный handler в бесконтрольной goroutine.
Рестарт не повторяет задачи с неопределённым результатом.

Старые доставки проверяют session и состояние отображения перед raw egress.
Уже отправленный HTTP-запрос невозможно отозвать: он может завершиться в старом
топике, после чего cleanup удалит его; в новый topic ID его не перенаправляют.

## 3. Control, миграция и совместимость

Использовать текущую delivery queue с kind `health` и стабильными event IDs:
`operation ID + revision` для создания, `session/topic + revision` для cleanup.
Смена причины или восстановление создаёт новую ревизию; очередной sweep того же
исхода не создаёт сообщение. Изменение случая и enqueue должны быть атомарны.
Это локальные storage-методы для Sync, без общего рефакторинга health-подсистемы.
Control сообщает название/ссылку на чат, что известно, что продолжает работать,
и действие off/on либо ручное удаление неизвестного остатка.

Миграция аддитивная и повторяемая:

- Активные bindings/drafts и их execution-состояние сохраняются. Старые rows
  cleanup без восстанавливаемого состояния запуска проверяются по receipts;
  отсутствие данных не трактуется как разрешение replay.
- Marker `sync.topic_create.<session>` с известным binding конвертируется в
  подтверждённую операцию. Без binding — в unknown конкретной цели. Старое точное
  отправленное имя в marker отсутствует: текущий title нельзя выдавать за него;
  такую операцию автоматически по имени не восстанавливать, сообщить в Control.
  Пока её нельзя исключить как источник неизвестного события, не присваивать
  это событие новой операции только по имени. Прямые ответы новых create
  продолжают подтверждать свои операции и не блокируют остальные чаты.
- После успешной конвертации удалить старый marker и глобальный gate. Записи
  существующих bindings с неизвестным исходным названием обозначить как legacy;
  новое неизвестное событие не присваивать им по догадке.
- Legacy `draining` перевести в off с сохранением работ и cleanup без новых
  interrupt. Уже отправленное старой версией прерывание отменить невозможно.
- Startup recovery, cleanup, callback expiry и queued deliveries учитывают
  все сессии и новое состояние deleted. Restart сохраняет active/off.

Выкладывать согласованный комплект storage + handlers + recovery. Старую версию
нельзя безопасно запускать поверх новых detached rows: она не знает их семантику.
При необходимости отката использовать совместимую исправленную версию либо
остановленную установку с резервной копией БД; не восстанавливать старую БД
поверх продолжающихся запусков. Выпуск и перезапуск выполняются отдельным шагом
после реализации, а не в рамках подготовки этого плана.

## 4. Порядок реализации

Каждое приращение начинается с поведенческих тестов. Пункты 1–4 составляют
минимальный полезный результат для исходного сбоя; полный согласованный объём
включает также безопасный off/on. Частичный результат не выдаётся за весь фикс.

| Шаг | Результат и границы | Проверка / условие перехода |
| --- | --- | --- |
| 0. Проверить внешние предпосылки | Подготовить воспроизводимые opt-in probes на тестовом контуре; зафиксировать версии и очищаемые тестовые объекты | Потерять только ответ create, получить собственное событие; для Telegram-origin turn проверить approval и input в Codex при сохранённом writer connection. Не вмешиваться в пользовательские запуски |
| 1. Журнал создания | Model/storage, схемы, транзакции подтверждения и уведомления, миграция markers | Fresh/old DB, повтор миграции, rollback, reopened store, no duplicate target intent. Коммит `feat(sync): persist topic creation operations` |
| 2. Приём событий | `telegram/api.go`, `bot.go`, отдельный daemon handler, replay сохранённых событий | Admission до store; событие без text; ошибка записи не продвигает offset; known ID и оба порядка подтверждения. Коммит `feat(telegram): recover topic creation from service events` |
| 3. Общий путь создания | Activation/discovery, `/newchat`/projects и external launch; убрать глобальный stop; async intent processing | Unknown первой цели не мешает второй, retry после crash не создаёт дубль, одинаковые/обрезанные имена, все источники. Коммит `fix(sync): isolate uncertain topic creation` |
| 4. Завершить восстановление создания | Late confirmation, Control revisions, off/late-create cleanup, external request continuation | Позднее событие создаёт только draft/binding; не повторяет start. External request с unknown create не получает обычный Retry, создающий новую операцию; после подтверждения продолжает только если request ещё разрешён и session active. Коммит `fix(sync): reconcile late topic confirmations safely` |
| 5. Независимое наблюдение за работой | Сохранение execution rows после удаления TG; общий read/terminal path вне current session; drafts presentation state | Два параллельных turn, active/unknown draft, failed terminal persistence, restart, освобождение lease только после сохранения результата. Коммит `refactor(sync): retain execution state after topic removal` |
| 6. Новый off/on | Короткий off, guarded prepare/IO/commit для dispatch, async admission; force alias; historical owner checks | Off во время RPC, approval/input, unknown dispatch; поздние ответы; повторный on и новый ввод без второго turn. Проверка через Bot.Run, не только прямой вызов Service. Коммит `fix(sync): disable presentation without interrupting Codex` |
| 7. Интеграция и документация | ADR-032/033/034 и актуальная семантика ADR-024/026/027, contract matrix, regression map; убрать заменённые gates/drain code | Полная матрица ниже, свежий review, live readback; коммит `docs(sync): document best-effort recovery and non-interrupting off` |

Шаги 1–4 можно проектировать и тестировать независимо от передачи approval в
Codex. Шаги 5–6 зависят от второй проверки шага 0. Если Codex не показывает или
не позволяет ответить на pending request другого соединения, сохранить одно
соединение недостаточно. Тогда сначала установить поддерживаемый App Server
путь доступа к запросу; если его нет — вернуться к пользователю с конкретным
ограничением. Не подменять требование автоматическим approve/deny, зависанием
без доступного ответа или сохранением Telegram-топика вопреки off.

Точно так же неполучение собственного события не отменяет изоляцию ошибки:
unknown остаётся в Control и off/on работает, но приёмку восстановления через
событие нельзя объявить выполненной без выяснения причины.

## 5. Проверка результата

| Требование спецификации | Различающий сценарий |
| --- | --- |
| 1–2: восстановление и идемпотентность | HTTP success/event в обоих порядках; crash между ними; потерянный ответ; повтор update; SQLite failure при bind и последующее открытие БД |
| 3: безопасные имена | Два одинаковых названия, одинаковый результат усечения, rename Codex во время запроса, старое unknown + новая сессия, late duplicate, событие чужого автора/группы |
| Миграция неизвестного имени | Legacy marker без исходного имени → off/on → новое создание с потерянным ответом → позднее событие старой операции: новая привязка не возникает, Control объясняет неоднозначность |
| 4: отсутствие общей блокировки | Первая create unknown, следующие успешны в этом и следующем проходе; после restart первая не отправляется вновь; штатная expiry/recreation успешного topic всё ещё работает |
| 5: работа продолжается | Вызвать off через настоящий update loop при заблокированном ответе RPC; затем разблокировать. Число turn/start не выросло, interrupt/automatic response/Close не вызваны; ответить на pending approval/input через Codex и дождаться terminal |
| 5: draft и внешние запуски | Off между thread/start и turn/start; unknown без thread ID; late event после закрытия request; неизвестный create не превращается в обычный Retry; новый топик не обходит старого writer owner |
| 6: очистка и старая сессия | Delete timeout, повторное удаление уже отсутствующего topic, restart off, поздний create после off и после нового on; stale callback/message/delivery не воздействует на новый binding |
| 7: live evidence | Тестовый create с искусственно потерянным ответом, событие и durable binding; readback User/Status/Final; off/on во время тестового Codex turn, continuation и terminal readback |
| Прозрачность | Telegram недоступен во время ошибки; после восстановления один актуальный случай и затем recovery, без сообщения каждый sweep; crash между изменением случая и enqueue не теряет уведомление |

Запускать целевые Go-тесты изменённых пакетов, затем `go test ./...`, targeted
`go test -race` для creation/dispatch/off/cleanup/recovery, `go build -buildvcs=false ./...`,
`git diff --check` и обязательный repository secret/local scan. Свежий reviewer
проверяет brief, diff, тесты и фактическую валидацию по AGENTS.md.
Live QA использует отдельные тестовые объекты и существующий poll consumer:
второй `getUpdates` на том же bot token может перехватить подтверждения.

## Основания и границы уверенности

План основан на текущих `internal/daemon/sync*.go`, `external_dispatch.go`,
`internal/telegram/{api,bot,egress}.go`, `internal/storage/store_sync*.go`,
`internal/appserver/writer_manager.go` и перечисленных контрактах.

Bot API подтверждает обновление при следующем `getUpdates` с большим offset;
хранит недоставленные обновления не более 24 часов. Событие создания содержит
имя, а ID берётся из сообщения. `deleteForumTopic` удаляет топик вместе с историей.
Эти API не дают гарантии получения события после длительной недоступности.
Источники: [getUpdates](https://core.telegram.org/bots/api#getupdates),
[ForumTopicCreated](https://core.telegram.org/bots/api#forumtopiccreated),
[deleteForumTopic](https://core.telegram.org/bots/api#deleteforumtopic).

Согласованные продуктовые решения определены. Начать реализацию можно с probes
и журнала создания; готовность зависимой части off/on требует доказательства
доступности ожидающих действий через Codex. Подготовка плана не выполняет
проверки Telegram или App Server с побочными эффектами.

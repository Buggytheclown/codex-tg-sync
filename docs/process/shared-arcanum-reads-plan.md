# Общие чтения Арка: первый раунд реализации

Дата: 2026-11-13. Основание: `shared-arcanum-reads-spec.md` и согласованный
объём первого раунда. База кода: `a780743`. Реализация выполнена. Результаты проверок — в
`shared-arcanum-reads-validation.md`.

## Объём и решения

Выполнить пять улучшений: переиспользовать авторский поиск, разделять общие
наблюдения между потребителями, читать только нужные ресурсы, публиковать
полученные статусы в футеры и полностью удалить зависимость от браузера.

Уточнение пользователя 2026-11-13 заменяет прежнее решение сохранять сетевые
интервалы Sources/правил и отдельный пятиминутный обход футеров. Теперь данные
получаются по единому расписанию ресурсов; поллеры и UI используют эти данные.
Фиксируем 30 секунд для search, 5 минут для comments/checks, 10 минут для get.

Done исключается и из регулярной загрузки `/v1/task-cards`, и из фонового
получения данных Арка ради этих карточек. Подтверждённые Merged терминальны.
Просмотр Done доступен по явному запросу из локальной БД.

Новый внешний сервис, dependency, экран Sources и таблицы БД не нужны.
Внутри демона нужен один владелец сетевого расписания общих ресурсов.
Независимых сетевых обходов футеров, Sources и задач больше не остаётся.

## Итоговое расписание запросов в Арк

| Ресурс | Период / ограничение | Единица объединения | Когда нужен |
|---|---|---|---|
| `pr search` | Каждые 30 секунд, не более одного обхода в 30 секунд на общий query | Точный query + единая проекция полей + page size | Активные карточки вне Done, правила в Polling и Sources |
| `pr comments` | Не чаще одного чтения в 5 минут на PR | Canonical PR ID | Только comment-условия и их необходимый baseline |
| `diff checks` | Не чаще одного чтения в 5 минут на PR | Лимит по PR ID; результат привязан к published diff ID | Только условия падения обязательных checks |
| `pr get` | Не чаще одного чтения в 10 минут на PR; регулярного обхода нет | Canonical PR ID | Только неизвестный автор или недостаточный search-ответ |
| Done / подтверждённый Merged | Ноль запросов специально ради них | Учитывается независимый активный спрос на тот же PR | Только локальное сохранённое состояние |

Первое необходимое чтение нового ресурса разрешено сразу, если его общий
срок ограничения ещё не установлен. Повторное arm/rearm, смена настройки,
новая карточка/вкладка, ручной refresh и restart не обнуляют этот срок.
Для checks новый diff также не сбрасывает пятиминутный лимит по PR: в очередной
раз читать актуальный опубликованный diff, пропуская вытесненные ревизии.
Comments и checks одного PR обслуживаются общим медленным раундом раз в
5 минут: состав нужных ресурсов объединяется до начала раунда. Добавление
второго ресурса между раундами ждёт общего следующего срока, а не запускает
отдельный несогласованный цикл. Каждый ненужный ресурс при этом пропускается.
Нет потребителей — нет запроса. Нельзя называть get раз в 10 минут обязательным:
при достаточном search его число равно нулю.

Каждая строка таблицы задаёт частоту начала логического чтения ресурса,
а не число HTTP-запросов: одна пагинация может содержать несколько страниц.
Одинаковый query не повторяется для каждой карточки или каждого поллера.
Разные необходимые author/assignee query остаются отдельными обходами.
Для одностраничных ответов средняя нагрузка после первоначальной загрузки:
`2 × Q + C / 5 + K / 5 + G / 10` команд в минуту, где Q — число общих search
query, C/K — число PR с нужными comments/checks, G — число PR с продолжающейся
необходимостью fallback get. При пагинации каждое слагаемое умножается на
соответствующее число страниц. Это расчёт расписания, а не замер трафика.

Пример: пять PR одного автора в одном подходящем search, только статусы —
2 команды в минуту суммарно, ноль get/comments/checks. Если всем пяти нужны
ещё comments и checks, то при одностраничных ответах получается в среднем
4 команды в минуту: 2 search + 1 comments + 1 checks. Отдельный discovery
query для ревью добавляет ещё 2 команды в минуту, если занимает одну страницу.
Запуски распределяются по времени; среднее не обещает отсутствия пиков на старте.

Ожидаемая задержка обнаружения при исправном API и свободной очереди — до
30 секунд для статусов/нового head/ревью и до 5 минут для ответов/checks плюс
время запросов и локальной обработки. Fallback get может задержать выяснение
неполного статуса до 10 минут. Изменение, полностью случившееся между чтениями,
не гарантируется к обнаружению, включая failure → success → failure за 5 минут.

## Подтверждённые контракты CLI

- Установленный pr get использует v2. В новом нормальном пути он не нужен:
  остаётся только редким fallback при недостаточном search-ответе или для
  определения неизвестного автора. Он не выполняется для каждого PR заранее.
- `pr search` отдаёт несколько PR с common_status и сведениями о ревизиях.
  Один полный набор полей используется во всех новых списочных чтениях.
- В проверке на одном наборе результат limit=2 совпал с объединением limit=1,
  offset=0 и offset=1. Ответы содержали total_count=2. Но --all с limit=1
  вернул одну запись и has_next=false. В коде установленного CLI цикл --all
  смотрит только page.has_next, а total_count в итог не переносит.
- Поэтому приложение читает страницы явно, без --all. Отсутствующий PR нельзя
  считать Merged. Полнота поиска и наличие конкретной положительной записи —
  разные гарантии.
- Live pr search с common_status(merged) вернул две записи: status=published,
  full_status=merged, common_status=merged, author и данные ревизий. Для одной
  записи get подтвердил status=merged. Ранее проверенный full_status=open
  также совпал с get status=open. Это подтверждает search-first путь для
  перечисленных сценариев. status=published не является lifecycle=open:
  lifecycle и факт публикации нормализуются раздельно.

## Архитектура

```text
активные PR-карточки / правила / Sources → общий набор потребностей
                                                   │
                          Collector + SharedReader → CLIClient → Арк
                                  │
                                  ├→ status publisher → SQLite → HTTP/SSE → UI
                                  └→ новые наблюдения → Runner / Checker → прежние actions
```

### Один владелец сетевого расписания

В `internal/arcanumreview` разделить search pages, get, comments и checks.
CLIClient отвечает за один физический вызов страницы, JSON и валидацию.
Общий collector задаёт интервалы и собирает завершённые чтения. SharedReader
объединяет совпадающий IO и хранит последнее наблюдение ресурса между проходами;
он не принимает решений о запуске чатов. Старый rulePRClient удаляется.

Runner/Checker и UI не запускают собственный обход и не дочитывают ресурс
в обход collector. Они регистрируют потребность и используют покрывающие её
общие наблюдения. Прежний metadata worker заменяется регистрацией спроса
футеров и публикацией статусов; отдельного сетевого fallback каждые 5 минут нет.
Отсутствующий ресурс означает ожидание ближайшего разрешённого чтения,
а не немедленный get/comments/checks из Check.

Потребности собирать по всей активной доске и правилам до сетевого раунда.
Пять карточек одного автора не разбиваются на независимые metadata batch,
повторяющие один search. Подходящий query Sources переиспользуется для карточек
и правил. Superset query может заменить более узкий только при доказанной
достаточности положительных строк и полноты для discovery. Нельзя считать
разные query одинаковыми только по совпадению автора.

Ключи результатов: search + точный query + единая проекция + page size,
comments + PR ID, checks + published diff ID, get + PR ID. Ограничитель checks
при этом отдельный, по PR ID: изменение diff не создаёт новый быстрый бюджет.
Полученные полезные строки search раздаются всем заинтересованным потребителям,
а не только инициатору чтения. Массивы/карты возвращаются без возможности
изменить общий результат через одного из потребителей.

Отдельно хранить canonical PR ID → author как подсказку идентичности, не статус.
Использовать discovery/search, source_author или первый необходимый get.
Подсказка переживает очистку временных страниц и restart через существующее
хранилище состояния; get не возвращается в каждый сетевой раунд.

### Ограничения, хранение и ошибки

- До начала сетевого чтения резервировать его общий `NextAllowedAt` по времени
  исходной попытки. Хранить сроки в существующем daemon_state, чтобы restart,
  повторное добавление карточки и rearm не позволяли обойти 30 секунд / 5/10 минут.
  Для каждого метода резервировать срок отдельно в момент отправки первой
  страницы, после получения слота исполнителя. Между резервированием и
  запуском команды нет очереди. Comments и checks одного PR входят в общий
  раунд, но у каждого свой фактический старт. Следующий раунд допускается
  по максимальному из сохранённых сроков этих методов, в том числе после restart.
  Не удалять срок до его истечения, даже если потребитель временно исчез.
  При ошибке сохранения резерва новый IO не начинать; сообщить локальную ошибку.
- Последние успешные observations и их resource coverage живут между проходами
  для текущих потребителей; cache hit не меняет timestamps и не продлевает TTL.
  После restart отсутствие payload не отменяет сохранённый cooldown: потребитель
  ждёт ближайшего разрешённого чтения. Не хранить в памяти архив всех PR.
- В один момент выполняется не более одного чтения общего ключа. Новый
  потребитель присоединяется к нему, если допустимы его исходные времена,
  либо ждёт следующего разрешённого чтения. Нет параллельных дублей одного ключа.
- Смена head/common_status, настройка правила или отсутствие свежего baseline
  не обходят лимит comments/checks/get. Если нужна инициализация после arm,
  читать baseline не раньше arm и не раньше сохранённого NextAllowedAt;
  до этого ожидание не потребляет событие и не продвигает курсор.
- По ошибке сохранять последнее хорошее значение, помечать неудавшуюся попытку.
  Не выдавать ошибку за пустые comments, успех checks, отсутствие PR или Merged.
  Потребитель, ждущий расписания, не считается ошибкой и не получает новую
  LastAttemptAt/LastSuccessAt только от локального сравнения старого кеша.
- Вызовы CLI из collector используют ARCANUM_CLI_RETRY_MAX_ATTEMPTS=1:
  скрытые быстрые retry не обходят ограничения. Ошибочная страница завершает
  текущую попытку; повтор начинается не раньше следующего срока ресурса.
  Учитывать Retry-After/backoff, если он требует более долгого ожидания.
  Цепочка разных страниц одного чтения допустима и считается отдельно.
- Физический запрос принадлежит контексту демона с bounded CLI timeout.
  Отмена одного ожидающего не отменяет запрос, нужный другому; остановка
  демона отменяет все чтения. Mutex не удерживается на IO. Нельзя создавать
  goroutine на каждый PR списка или задерживать search на сетевых comments/checks.
  Медленные ресурсы имеют отдельную ограниченную очередь внутри collector.

### Новые факты запускают локальные проверки

Успешный search сразу публикует статусы футеров и будит заинтересованные
Sources/правила. Они используют тот же результат без get и повторного search.
Comments/checks после своего редкого чтения будят только соответствующих
потребителей. Bounded Runner сохраняет generation fences, приоритет Done,
дедупликацию и прежние actions; дополнительные сетевые вызовы ему запрещены.
Вызов Collector не исполняет actions из сетевого callback.

Legacy interval_seconds PR-правила больше не является частотой запросов Арка.
Новое явно согласованное расписание 30 секунд / 5 минут / 10 минут заменяет
прежние сетевые интервалы. Локальный cron и действия по его расписанию прежние.
В API/диагностике Next check отражает ближайшее разрешённое получение нужного
ресурса, включая ожидание baseline. В редакторах Sources (forms.tsx) и
PR-правил (PollingRules.tsx) заменить «Check every · seconds» на доступное
только для чтения расписание применимых ресурсов. Старые конфиги с
interval_seconds принимаются и сохраняются при редактировании остальных полей.

Регистрация для /pollers, отображение stale и расчёт общего recovery используют
ожидаемый срок следующего наблюдения с учётом лимита и очереди. Для терминального
PR без будущих чтений явно хранить состояние завершённого наблюдения. Если у
задачи есть другие активные PR, их ошибки и сроки по-прежнему участвуют в health.

Статусные группы проверять на каждом подходящем новом search. Группа с
comment/check-условиями проверяется после получения необходимых новых
ресурсов; старый failure из пятиминутного кеша не соединяется с новым
Request changes для ложного AND. Для такого раунда фиксируется последняя
полная search-строка возрастом до 30 секунд, generation, published diff и
чтения comments/checks, начатые в общем медленном раунде этого PR. Разные
потребители не создают несовпадающие независимые циклы этих ресурсов. Если diff
сменился, не применять checks старого diff к новой строке: ждать разрешённого
чтения актуальной ревизии. Статусные OR-ветви и другие PR при этом продолжают
работать. Уже Merged обрабатывается до требования optional coverage.

### Поиск и опубликованные ревизии

Список кандидатов Source запрашивается с прежними query и правилами отбора.
Расширить ответ данными common_status/active_diff_set/diff_sets; положительные
строки могут обеспечить review info для последующего чтения того же PR.
Список известных авторов не заменяет discovery новых назначенных PR.

Авторский поиск для review info выполняется один раз на общий 30-секундный
раунд query, с переиспользованием страниц всеми его потребителями. Читать
страницы только до нахождения необходимых известных PR; не завершать весь
исторический архив автора ради одного найденного
PR. Полный проход требуется для discovery-списков. Каждое чтение списка ограничено
действующим timeout; неполный результат явно отмечается как неполный, не превращается
в вывод «такого PR нет». Не сохранять в памяти поля ненужных исторических PR
за пределами текущего чтения и набора активных потребителей.
Неизменный/repeated page, конфликт total/count,
неожиданно пустая промежуточная страница и ошибка следующей страницы — ошибки
полноты. Положительная проверенная строка остаётся полезной для своего PR.

На странице использовать offset/limit и total_count, если оно предоставлено;
иначе has_next, если предоставлен достоверный флаг; иначе читать до короткой
страницы, включая контрольный пустой запрос для точного кратного limit.
CLI --all больше не используется приложением. Тесты включают случай, когда
has_next отсутствует, а total_count больше размера страницы.

Выбор опубликованной ревизии сохраняет текущую логику snapshot.go: активный
опубликованный diff либо последняя опубликованная ревизия; draft head не
становится событием New commit. Поля одной v1 строки нормализуются явно:
full_status — lifecycle, common_status — агрегированный статус для футера и
Request changes, status/diff_sets — публикация ревизии. В противоречивом или
неполном ответе не угадывать значения. На пять PR одного автора в благоприятном
одностраничном случае достаточно одного search вместо пяти пар get+search,
если эта выборка содержит все пять PR и все требуемые поля. Это не обещание
существования отдельного batch-by-ID endpoint.

Если нужная запись отсутствует, искать её по подходящему полному query с
явной пагинацией, не ограничиваясь открытыми PR: исчезновение из open-списка
не доказывает Merged. Только если достаточную строку получить не удалось,
разрешён fallback get для точечного lifecycle/author по общему лимиту
один раз в 10 минут на PR, а не после каждого 30-секундного search. Open get без review info
не подменяет полноценный search snapshot и не считается успехом Request changes
или New commit. Отсутствие/ошибка поиска никогда не равнозначны merge.

### Подтверждённый Merged — терминальное наблюдение

Merged подтверждается положительной записью search по точному PR ID с
full_status/common_status=merged либо достоверным fallback get status=merged.
Store schedule исключает уже подтверждённые Merged, SharedReader и publisher
удерживают терминальный факт по canonical PR ID; новые get/search/comments/checks
ради этого PR не начинаются. Существующие успешные merged записи кеша участвуют
в этом правиле сразу после запуска демона.

Терминальные факты хранятся по canonical PR ID независимо от существования
самостоятельной PR-карточки: правило Task/Schedule тоже может ссылаться на PR.
Использовать существующую keyed-by-pr_id таблицу metadata; не создавать карточку
ради факта. Перед сетевым чтением можно загрузить нужные терминальные факты из
Store по ID, с локальным scope кешем. Для текущих нужных карточек/правил загрузить
их перед запуском workers. Не держать весь исторический ledger в памяти.
Очистка footer/hint состояния не удаляет сохранённый терминальный факт.

Metadata projection для такого PR не получает stale только от возраста,
next_check_at больше не является причиной опроса. Publisher pending состояние
останавливает новые чтения сразу, не дожидаясь SQLite. После успешной записи
терминальность переживает restart. При утрате ещё не сохранённого результата
из-за аварии допустима повторная верификация, а не выдуманный persisted факт.

Если задача осталась в Polling без правила PR merged → Done, она не переносится
самовольно: её правила получают сохранённый терминальный факт без сетевого IO.
При наличии правила оно исполняется по прежнему контракту; другие PR той же
задачи продолжают проверяться. Поздние не-Merged ответы не отменяют Merged.
Замена привязки на другой PR использует другой canonical ID, не наследуя этот
факт. Done нашей карточки сам по себе терминальность PR не доказывает.

Уже Merged PR может случайно присутствовать в общем ответе поиска, выполненного
ради других PR или discovery. Это не отдельный опрос такого PR: он не создаёт
дополнительный due job, запрос, baseline/comment/check refresh или API page,
нужную только для уже терминального PR.

Обрабатывать terminal до needs/coverage проверки: отсутствие comments/checks
для Merged не является ошибкой всего раунда. Условие PR merged получает true;
остальные interaction/check условия такого PR не совпадают, их соответствующие
курсоры сохраняются. OR-группа с PR merged может сработать, группа, требующая
дополнительно ответов/checks, — нет. Правила других PR продолжают работу,
приоритет Done сохраняется. Не вызывать обычный неполный snapshot путь, который
вместо этого запросил бы checks/comments или вернул missing-coverage error.

### Done: загрузка по запросу и отсутствие фонового спроса

Разделить активную доску и завершённые карточки на уровне чтений Store/API:

- `GET /v1/task-cards` по умолчанию возвращает только `column != done`.
  Оба SQL-запроса компактной проекции — карточки и launch-request summaries —
  ограничиваются этим набором до сборки DTO; фильтрации готового полного
  списка в HTTP или UI недостаточно.
- Явный `GET /v1/task-cards?column=done` возвращает только Done из локальной
  БД. UI вызывает его при Show Done, включая восстановленное при открытии
  страницы предпочтение показа. Результат хранится отдельно от активных cards;
  обычный refresh не заменяет и не удаляет загруженный Done-набор.
  Периодический таймер, focus, SSE invalidate и reconnect не перечитывают Done,
  даже когда колонка показана. Повторное явное открытие допускает новое чтение.
- SSE reconciliation использует только активную компактную проекцию.
  Не оставлять скрытый полный ListTaskCards/legacy ListTasks ради вычисления
  hash, числа Done или предварительной загрузки архива. Изменение только
  Done-карточки не запускает регулярную перезагрузку архива.
- Успешный move в Done удаляет карточку из активного UI и обновляет уже
  загруженный Done-набор из ответа команды; reopen делает обратное.
  При активной загрузке Done поздний ответ сверяется с принятыми версиями
  и переносами, чтобы не вернуть карточку в старую колонку. Внешний reopen
  становится виден через обычный active refetch; его ID убирается из Done-кеша.
- Точечные `GetTaskCard(id)` и `GET /v1/tasks/{id}` продолжают читать Done.
  Deep link/выбранная Done-карточка открывается по ID независимо от отсутствия
  в активном списке; её отсутствие не трактуется как удаление. Сохранить
  защиту версий/черновиков и обработку настоящего 404. Detail Done загружается
  по выбору или явному действию, без периодического refetch от общего
  detailRevision, focus, SSE и reconnect; ответы собственных команд обновляют
  локальное состояние. Конфликт при сохранении требует явного перечитывания.
- Существующие связи Task/PR с Done не исчезают из-за сокращения списка.
  Для активного Task краткие ссылки на связанные Done PR получать локальным
  запросом только связанных записей, без полных Done DTO/polling/request
  payload; при выборе открывать detail по ID. Для Done-родителя и поиска
  кандидатов на связь разрешены локальные чтения по явному открытию редактора.
  Это не возвращает весь архив в регулярную загрузку и не создаёт Arc IO.
  Legacy `GET /v1/tasks` сохраняет контракт, но новый UI/SSE не использует
  его для обхода исключения Done.
- Заменить Runner.PollOnce → ListTasks при регистрации health на компактную
  выборку активных pollers (ID, название, тип и расписание). Сверять с ранее
  зарегистрированными ID, чтобы переход в Done и удаление отключали старую
  регистрацию. Закрытая доска также обходится без чтения полного архива,
  thread snapshots и истории launch requests.

Сетевой спрос футеров включает только PR-карточки вне Done. Перевод в Done
снимает спрос футера на новые search/get/comments/checks и дополнительные
страницы поиска, включая bootstrap неизвестного автора. Перед началом нового
IO перепроверить актуальность потребителя: уже выбранный до переноса due item
не должен начать новый запрос только ради Done. Начатый сетевой запрос может
bounded завершиться; его ответ не возвращает карточку в расписание.
Удаление одного потребителя не отменяет общий IO, нужный другим потребителям.

Done не является глобальным запретом чтения canonical PR ID. Другой активный
PR-футер, правило задачи в Polling или Source могут независимо нуждаться в том
же PR. Их чтения продолжаются; случайно полученный общий статус допускается
сохранить, но Done не требует отдельного запроса, retry или страницы.
Не записывать Merged на основании Done и не стирать metadata/terminal ledger.

Reopen снимает ограничение Done; невмерженный PR снова участвует в общем
search раз в 30 секунд. Сроки comments/checks/get при этом не сбрасываются.
Известный Merged остаётся терминальным. Show Done, выбор карточки, detail read
и её редактирование в Done сами по себе не возобновляют metadata polling.

### Needs и совместимость курсоров

В Checker вычислять нужные ресурсы до сетевых чтений. Источник needs — не
только подпись события: учитывать текущий PRCursor, смену generation, source
baseline и поля существующего event fingerprint.

| Сценарий | Чтения первого раунда |
|---|---|
| Только отображение статуса вне Done | Подходящий pr search с full_status/common_status; известный Merged — локальный терминальный факт |
| Просмотр Done | Только сохранённые локальные данные по явному запросу; отдельного Arc IO нет |
| Чистое ожидание PR merged | Подходящий pr search; после подтверждения только локальный терминальный факт |
| Request changes / New commit | Подходящий pr search, включая head/diff для нынешних Matches |
| All answered / All resolved | pr search + comments |
| Failed merge checks | pr search + checks выбранного published diff |
| Первичное arm/rearm или source baseline | Дополнительно comments только для настроенных условий об ответах/закрытии замечаний; search-only условия их не требуют |

Для перечисленных search-only условий не сохранять скрытую обязательную
зависимость от comments через старый Tracked. ComparePR обновляет comment cursor
только если текущим условиям нужны comments; иначе сохраняет comment state без
фиктивного чтения и потребления replies. При добавлении All answered/resolved
generation меняется и выполняется необходимая свежая инициализация после arm,
с ожиданием общего разрешённого срока comments при действующем cooldown. Head/diff
из search сохраняются для нынешних Matches. Это изменение legacy внутреннего
cursor bookkeeping проверить тестами редактирования правил, rearm и dedup:
оно не должно повторить запуск или потерять настоящий ответ в comment-условии.

Добавить coverage к входному наблюдению ComparePR: не прочитанные необязательные
факты не очищают существующие comment/head/status поля курсора. Если условию
или baseline эти данные необходимы, для каждой группы различать три исхода:
получены данные для сравнения (условие истинно или ложно), ожидание нужного
чтения, ошибка выполненного чтения. Сохранять Matches и курсор ожидающей или
ошибочной группы. Обновлять их только у проверенных групп. В AND отсутствие
обязательного факта откладывает сравнение всей группы. Готовая OR-ветвь может
дать событие в том же проходе, даже если у другой ветви ожидание или ошибка.
Ошибку отдельного чтения отражать в диагностике этого ресурса.
Runner принимает результат готовой ветви через обычную транзакцию с проверкой
generation. Пробуждение по новому факту запускает заинтересованное PR-правило
даже при старом будущем next_check_at задачи или NextCheckAt правила.
При одном лишь ожидании записывается срок следующей проверки без изменения
курсора и времени последней попытки/успеха.
Сохранённые event keys и Matches не переписываются. Проверить partial coverage
на старых курсорах и при редактировании условия: samePollingIdentity сейчас
сохраняет курсор при смене списка условий. При несовпадении нельзя возвращать
скрытый обязательный comments в search-only путь: нужно явно разграничить
неактивное comment bookkeeping и инициализацию реально включённого comment
условия, сохранив уже принятые события и ответы существующих comment-правил.
Допустим необязательный coverage marker в JSON курсора без переписывания
старых записей; отсутствие marker означает старый полный формат. Тесты этой
границы предшествуют изменению ComparePR.

Для Source один подходящий search одновременно даёт discovery и PR facts.
PR review обнаруживает кандидата без get/comments/checks. Comments для baseline
дочернего ожидания читаются отдельно только если его условия действительно
требуют отслеживания замечаний; это не часть самого обнаружения ревью.
PR feedback с merge-check условием дочитывает checks. Здоровые кандидаты не
требуют comments. seedChildRules и consumed replies сохраняют смысл для
comment-условий; независимые OR-ветви не воспроизводят уже принятое событие.
При ошибке действительно необходимого baseline source cursor не продвигается.

### Публикация статуса без нового чтения

Успешный status bundle сразу передаётся в существующий arcanum_pr_metadata:
lifecycle + common_status для обычного PR, либо подтверждённый Merged. Успех
comments/checks для этого не требуется. Ошибка checks не делает свежий статус
футера неуспешным. Lifecycle-only open не изображает полный common_status.

Разделить время наблюдения и время записи. Один daemon-local status publisher
получает полноценные атомарные строки search вместе с исходными StartedAt/
FinishedAt и отдельные ошибки. Строка содержит lifecycle и common_status из
одного ответа; не склеивать старый lifecycle get с новым common_status поиска.
Положительный fallback Merged тоже является достаточным терминальным фактом;
обычный open get без common_status не публикуется как полный статус.

Publisher сохраняет последнюю успешную строку и последнюю необходимую попытку
для каждого наблюдаемого PR. Новые строки сравниваются по исходному времени,
а не времени записи; одинаковый cache hit не обновляет timestamps или deadline.
Подтверждённый Merged становится терминальным и не отменяется поздними open
строками, ошибками или ранее запущенными запросами. Комментарии/checks не
определяют успешность публикации статуса.

Все записи effect/fallback наблюдений и ошибок проходят через publisher;
прямого конкурирующего RecordPRMetadata из workers не остаётся. Один внутренний
обработчик последовательно пишет SQLite. Короткий mutex и pending map с одним
сигналом объединяют обновления; сетевой IO под mutex не выполняется. Состояние
ограничено текущими наблюдаемыми PR и pending записями, включая ссылки из правил
без PR-карточки. На старте/перед сетью загрузить нужные подтверждённые Merged
из существующего кеша. Остальные сохранённые значения
остаются последними известными, а не новыми наблюдениями.

Для невмерженного PR LastSuccessAt опирается на исходное чтение строки,
ожидаемое следующее обновление — на общий 30-секундный search. Последняя
успешная проекция и её stale/error marker сохраняют реальные исходные даты.
Не получать из этого marker новое право на немедленный IO; им управляет
только collector. Merged не становится stale только из-за возраста.

Ошибка записи футера не делает успешное наблюдение Арка ошибкой action-поллинга
и не откатывает курсор. Publisher сохраняет pending проекцию и повторяет только
локальную запись по существующему десятисекундному такту. Это не добавляет
search/get/comments/checks; следующие сетевые чтения остаются по общему
расписанию. Latest-only pending map не разрастается от каждого 30-секундного
наблюдения во время сбоя SQLite. Другие потребители продолжают использовать
полученные факты независимо от успеха записи футера.

Список спроса футеров — тонкая локальная проекция PR ID + author только для
PR-карточек вне Done. Он не загружает полные task payload и не обрезает спрос
первым LIMIT 10. Ограничение размера batch применяется к исполнению очереди,
а не к обнаружению всех заинтересованных PR одного общего search.
Удалённый/перепривязанный/Done footer снимает свою ссылку на ресурс; активное
правило или Source может удерживать другую. Не удалять pending запись,
неистёкший cooldown или сохранённый terminal ledger вместе с footer-ссылкой.

### Удаление логики браузерной активности

Удалить MetadataPresence, endpoint/options /v1/board-presence, hook
usePRMetadataPresence и связанные с ним тесты и reconnect-связку App.tsx.
Старые уже открытые UI могут получать 404 на прежние heartbeat, но это не
разрешает/запрещает работу worker и не пишет task events или Telegram health.
Не вводить совместимый фиктивный endpoint только ради старого bundle.

Удалить самостоятельный metadata network loop, refreshSince и принудительный
обход. Collector постоянно обслуживает общий спрос по таблице частот;
публикация в SQLite выполняется отдельно и не запускает сетевой fallback.
Сохранить обычные HTTP/SSE refetch, focus и reconnect активной доски: они читают
локальную проекцию, а не запускают запросы в Арк. Done-список и выбранный
Done-detail исключаются из этих автоматических чтений.

## Порядок реализации

1. **Контракты и пагинация.** Fixtures для v1/v2, единая search-проекция,
   явная пагинация без --all. Положительная строка, полнота discovery и
   идентичность опубликованной ревизии проверяются отдельно.
2. **Общее расписание и наблюдения.** Collector/SharedReader с fake clock,
   периодами 30 секунд / 5 минут / 10 минут, общей in-flight дедупликацией,
   persistent cooldown, очередью медленных ресурсов и CLI без скрытых retry.
   Спрос со всей активной доски объединяется до сетевых чтений.
3. **Потребители фактов.** Search будит Runner и publisher; comments/checks
   обновляют только нужные условия. Убрать прямой network path из Checker,
   старый rulePRClient и самостоятельный metadata network loop. Ожидание
   разрешённого baseline не является ошибкой и не продвигает курсор.
4. **Needs и курсоры.** Покрытие ресурсов, согласованные раунды AND/OR,
   search-only без comments/get, сохранение fingerprint/dedup и старых курсоров,
   terminal Merged до optional coverage. Тесты предшествуют смене ComparePR.
5. **Проекция и Done.** Один status publisher с исходными датами и локальным
   retry; исключить Done из сетевого спроса и обычных Store/HTTP/SSE чтений,
   сохранить явную загрузку, deep links, связи и переносы.
6. **Убрать presence и обновить контракты.** Удалить browser/HTTP presence,
   заменить настройку интервала в двух редакторах, перевести регистрацию,
   /pollers и recovery на фактическое расписание ресурсов, обновить ADR-035,
   API contract, regression map и заменённую спецификацию видимости.
7. **Совместная проверка и свежее ревью.** Проверить полный diff и реальные
   счётчики ресурсов/страниц. Коммит/установка — по отдельному запросу.

## Проверки и доказательство выигрыша

- Fake clock фиксирует старты команд. Comments стартует в 00:00, checks
  задерживается в очереди до 00:40. В 05:00 следующего checks ещё нет,
  первый разрешённый совместный раунд — 05:40. Повторить с перезапуском
  после старта checks и проверить сохранённые сроки обоих методов.
- Интеграция Runner + SQLite: правило «Request changes OR Failed merge checks»
  со старым будущим NextCheckAt, сначала checks ждёт своего срока, отдельно —
  завершился ошибкой. Новый search с waiting_for_changes приводит ровно к
  одному принятому действию. Курсор и Matches непроверенной группы сохранены.
  Для AND действие ждёт покрытия обоих условий. У случая с одним ожиданием
  прежние LastAttemptAt/LastSuccessAt.
- С закрытой доской и большим архивом прогнать несколько тактов production
  Runner c health. Проверить отсутствие вызовов полного ListTasks/GetTask для
  регистрации, чтений snapshots и request history завершённых карточек.
  После move в Done поллер отключён и после reopen в Polling регистрируется.
- В обоих редакторах открыть старый PR-конфиг с interval_seconds, изменить
  другое поле, сохранить и открыть снова. Видно действующее расписание.
  С fake clock проверить /pollers и общее recovery между редкими чтениями
  (checks 5 минут, fallback 10 минут), после просрочки и для терминального
  PR без следующего чтения. Отдельная реальная ошибка блокирует recovery.
- Для пяти открытых PR одного автора, только футеры, одна страница на query,
  сравнить установившиеся циклы за пять минут. До изменения пять пар get+search
  дают 10 команд. После изменения десять общих search дают те же 10 команд
  и обновляют статусы каждые 30 секунд. Проверять число команд на выборку,
  отсутствие дублей и время от наблюдения до доступности карточке и правилу.

- Counting CommandRunner: пять PR в подходящем одностраничном search — один
  search, ноль get/comments/checks для статусов, merge, changes и commit. Два
  потребителя не удваивают нужные comments/checks. Страницы считаются отдельно.
- Store/HTTP: смешанный набор активных/Done карточек — обычный `/v1/task-cards`
  возвращает только активные; `?column=done` — только Done. Обе SQL-выборки
  проекции исключают Done до сборки DTO, точечные чтения Done работают.
  Большой Done-набор не увеличивает объём DTO/request summaries обычного списка.
- SSE/UI: Done не участвует в reconciliation hash как полный DTO. Show Done
  делает одну явную локальную загрузку; таймер, focus, invalidate, reconnect
  и второе окно не добавляют фоновых загрузок Done. Повторное открытие загружает
  заново. Обычный refetch сохраняет загруженный архив. Перенос/reopen во время
  загрузки не отменяется поздним ответом; deep link, выбранная Done-карточка,
  краткие связи с Done и version/draft protection сохраняются.
- Counting CommandRunner: единственная невмерженная PR-карточка в Done не
  вызывает Arc IO после тактов, restart, Show Done и detail read. Done с
  неизвестным автором не вызывает bootstrap get. Много Done перед активным
  PR не занимают batch LIMIT и не блокируют обновление активного PR.
- Перенос due PR в Done до начала IO исключает новый запрос и отдельные
  страницы ради него. Reopen восстанавливает обычное расписание по свежести;
  известный Merged не опрашивается. При независимом активном правиле/Source
  на тот же PR чтения продолжаются, Done не отменяет чужое ожидание и не
  подменяется Merged. Поздний ответ не возобновляет спрос Done-футера.
- Fake clock/counting runner: один общий одностраничный query за 60 минут
  даёт не более 120 search-обходов после первого чтения; пять карточек,
  два Sources и несколько правил не умножают совпадающий query.
- Comments и checks одного PR имеют интервалы начал чтений не менее 5 минут,
  get — не менее 10 минут. Отдельно проверить смену diff каждые 30 секунд:
  checks не начинают читаться каждые 30 секунд. Нет условий — ноль IO ресурса.
- Новый scope, rearm, новая карточка, reopen, UI refresh и restart с той же БД
  сохраняют cooldown; unknown author не даёт get на каждом search.
  После restart без payload ждать разрешённого срока, а не обходить лимит.
- CLI retry отключён для collector. Ошибка/429/timeout и неполная страница не
  создают немедленного повторного запроса; страницы разных offset/cursor
  считаются отдельно. Более длинный server backoff имеет приоритет.
- Одно физическое search-наблюдение сразу обновляет футер и будит все нужные
  Sources/правила. Они не ждут прежнего metadata обхода и не повторяют IO.
  Начало checks/comments не задерживает очередной search медленным ресурсом.
- Новый ответ без смены head и изменение checks того же diff обнаруживаются
  следующим разрешённым чтением. Не требовать обнаружения промежуточных
  состояний, целиком пропущенных пятиминутным периодом.
- Status-only OR-ветвь работает каждые 30 секунд; mixed AND не соединяет новый
  статус со старым cached failure. Проверить общий медленный раунд PR при
  добавлении второго ресурса, восстановлении разных сроков, смене diff при
  ожидании checks и rearm во время in-flight baseline.
- Пока baseline ждёт разрешённого чтения, нет ложного failure/успеха и движения
  курсора. После готовности не воспроизводится уже принятое событие.
  Partial coverage не меняет прежние event keys/Matches и не стирает cursor.
- Подтверждённый Merged не создаёт нового IO после тактов и restart, включая
  PR только в правиле без самостоятельной карточки. Поздний open/ошибка его
  не отменяет; отсутствие PR в open-списке не подменяется Merged.
  Другие PR задачи проверяются, приоритет Done и generation fences сохранены.
- Publisher: cache hit не омолаживает даты, поздний ответ не затирает новое
  наблюдение. Сбой SQLite повторяет только последнюю локальную проекцию;
  сеть продолжает общий 30-секундный режим, без дополнительных запросов ради
  записи футера. Pending map ограничен текущими PR, нет busy loop.
- Отмена одного потребителя не отменяет общий запрос другого. Остановка
  демона завершает чтения и ожидания без утечки goroutine.
- HTTP/UI интеграция: закрытая/скрытая/открытая доска, focus, reconnect и два
  окна не меняют расписание Арка. Done-сценарии из списка выше сохраняются.
- Контролируемое read-only сравнение: измерять query/PR, тип ресурса, starts,
  страницы, reuse/in-flight join, ошибки, duration и фактическую задержку
  карточек/условий. Отличать логические обходы, CLI starts и HTTP-попытки.
  Для нового collector single-attempt CLI — production policy, а не только
  приём измерения. Без трассы HTTP не объявлять число команд точным числом
  HTTP-запросов. Не включать приватные ID/заголовки/тексты/токены в public artifacts.

После targeted тестов выполнить go test ./..., targeted race для reader,
polling/storage/daemon, go build -buildvcs=false ./..., UI tests/build,
git diff --check и staged privacy scan. Live проверки проводить read-only
или на изолированной БД без реальных запусков; реальные UX проверки отдельно
отметить, если browser host недоступен. При последующей установке сохранить
Sync state, session и существующие задачи/requests; миграции данных нет.

## Готовность к реализации

Частоты этого раунда определены: search 30 секунд на общий query, comments
и checks 5 минут на PR, get только при необходимости с лимитом 10 минут на PR.
Это заменяет прежний план сохранения сетевых интервалов и metadata fallback.
Новые данные общие для локальных условий и футеров; редкие ресурсы могут
задержать соответствующее событие до своего следующего чтения. Done/Merged
не создают отдельного сетевого спроса. Реализация этого режима завершена. Список выше сохраняет
критерии приёмки; фактический охват проверок см. в regression map и отчёте реализации.

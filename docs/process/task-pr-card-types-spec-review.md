# Проверка спецификации Task / PR / Schedule

Дата: 2026-11-11. Проверен `task-pr-card-types-spec.md` и текущий код.
Это проверка требований перед реализацией; изменения приложения и живых данных
не выполнялись.

## Вывод

Основной сценарий реализуем. Явный тип, одна PR-карточка, ручная связь с Task,
колонка Review и независимый статус Арка согласованы достаточно для проектирования.
Найденное правило перехода старых данных закрыто решением пользователя
2026-11-11: PR-ссылки Task сохраняются в History, активное поле очищается,
связи остаются ручными. Граница редактирования PR определена в проверенном
техническом плане. Спецификация готова к реализации по этому плану.

## 1. Переход старых Task с PR-ссылкой — закрыто решением пользователя

В «Принятых решениях», п. 2, Task больше не имеет PR-поля. В «Сохранности и
эксплуатации» прямой PR предлагается убрать только после ручного связывания.
По проверенному частному снимку существуют такие пары Task разработки и
отдельной PR-карточки. При запуске новой версии до ручного связывания либо
останется запрещённое активное поле, либо ссылка исчезнет из доступного контекста.
Наличие отдельного PR не разрешает автоматически установить родителя: пользователь
явно выбрал ручные связи.

Пользователь выбрал сохранение прежней ссылки событием в History, очистку
активного поля и предложения ручных связей в частной карте. Автоматическое
связывание не выполняется. Решение внесено в спецификацию и план.
Отдельное уже принятое решение «оставить ручную Task и отвязать PR» сохраняется.

## 2. Изменение основного PR — граница контракта

Раздел «Статус Арка» требует обработать смену PR и конфликт старого поллинга.
Код позволяет редактировать/очищать `source_url`, при этом PR ID в правилах
ожидания находится отдельно. Простое обновление ссылки может показать новый
PR, а запускать исправления старого. Существующая проверка активного чата
сама по себе не доказывает согласованность ссылки и правил.

План должен определить атомарную валидацию смены: запрет очистки у типа PR,
проверка уникальности нового ID, сохранение текущих защит запуска и отказ
при несовместимых PR-правилах. Менять правила молча нельзя. Согласованное
изменение ссылки и правил можно сохранить существующей общей операцией.
Это техническое разрешение неопределённости, дополнительный продуктовый
выбор не требуется.

## Подтверждённая выполнимость и ограничения

- `internal/storage/store_tasks.go` сейчас ограничивает колонку SQLite CHECK
  четырьмя значениями. Review требует миграции таблицы, а не только новой опции UI.
- `store_task_outcomes.go` дедуплицирует карточки по source key. Два источника
  одного PR имеют разные namespaces. Для требования «одна PR-карточка» нужна
  каноническая PR-идентичность на всех путях создания, включая импорт.
- `internal/arcanumreview/snapshot.go` уже получает lifecycle и `common_status`
  через действующий CLI. Полный snapshot также читает комментарии и diff facts.
  Для футера достаточно отдельного чтения метаданных; семантику правил менять
  не требуется. Полный словарь UI-названий raw-статусов ещё не проверен; план
  не должен подменять неизвестный статус выдуманной готовностью к мерджу.
- `source_task_id` действительно хранит происхождение из Source. Нужна отдельная
  связь разработки. Одного parent ID у PR достаточно; общий граф не нужен.
- Компактная проекция (`store_task_cards.go`) позволяет добавить тип, parent ID
  и небольшой статус без загрузки детальных конфигураций на каждую строку.
- Напоминания и пинги из исходной проблемы не входят в согласованный объём.
  Новая доска делает ожидание видимым, но сама не гарантирует, что человек
  вспомнит пингануть ревьюера. Это явно отражено в спецификации, а не пропуск
  реализации.

## Что можно упростить

Оставить существующую модель карточки и жизненный цикл запусков. Добавить только
тип, канонический PR ID, одну родительскую связь и пассивный кеш метаданных.
Строки под Task строить из тех же компактных PR-записей. Не вводить отдельные
subtask-записи, перенос чатов, агрегированный статус родителя, новый механизм
запусков или автоматические связи по тексту.

## Ограничения проверки

Проверены исходники, текущие тестовые контракты и частный снимок классификации.
Новые тесты приложения не запускались: код не менялся. Новые API-поля Арканума
не предполагаются; будущая реализация должна проверить преобразование raw
статусов и read-only readback через существующий CLI. Динамический снимок карты
не заменяет проверку версий перед будущим применением.

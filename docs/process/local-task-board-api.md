# Local task board API contract

Go DTOs live in internal/model/tasks.go. JSON names are snake_case. `internal/tasks.New(store)` returns `*tasks.Service`.

Service methods (context first):
- `ListTasks(ctx) ([]model.Task, error)`
- `GetTask(ctx, id) (*model.Task, error)`; nil means not found
- `CreateTask(ctx, model.CreateTaskInput) (*model.Task, error)`
- `UpdateTask(ctx, id, model.UpdateTaskInput) (*model.Task, error)`
- `MoveTask(ctx, id, model.MoveTaskInput) (*model.Task, error)`
- `SetTaskPolling(ctx, id, model.SetTaskPollingInput) (*model.Task, error)`
- `AddChat(ctx, threadID, title) (*model.Task, error)`; idempotent, starts TODO
- `ListTaskEvents(ctx, id) ([]model.TaskEvent, error)`

Errors `tasks.ErrConflict`, `tasks.ErrInvalid`, `tasks.ErrNotFound` support errors.Is. Mutations require expected_version. Task update replaces editable title/description/source_url/config; polling settings use their own operation. Column values: inbox, todo, polling, done. Polling requires type, once/repeat mode, object config and action type return_task/resume_task/create_task (create_task also needs an owned child_definition). There is no enabled flag; column activates polling. Sources are tasks with create_task action. Execution is an existing ThreadSnapshotState projection, never separately mutated running state. Requests/history are read-only; pending prompt/settings are frozen.

Suggested routes: GET/POST /v1/tasks, GET/PATCH /v1/tasks/{id}, POST /v1/tasks/{id}/move, PUT /v1/tasks/{id}/polling, GET /v1/tasks/{id}/events, POST /v1/tasks/add-chat (thread_id,title). Successful task mutations return full Task. Lists return arrays. Errors use status 409 conflict, 400 invalid, 404 not found. Exact envelope/SSE can be selected by API owner.

Daemon must call MoveTask under its launch mutex, the same mutex spanning claim through definite dispatch. Store cancellation touches pending and starting requests with empty result thread/turn only; an already dispatched or ambiguous request is preserved. Store additionally guards claim/retry of cancelled tasks. Polling runner uses `ListDueTaskPolling(ctx, now, limit)` on Store and `AcceptTaskPollingOutcome(ctx, outcome, approvalTopicID)`; generation captures the due row. Acceptance is atomic with owned child definition copy, cursor, task event and frozen request. No external IO inside the transaction.

## Integration details

Default manual column is TODO. Source event children always start Inbox. A source's `polling.action` is `{type:"create_task", child_definition:{title,description,config,polling?}}`. The definition embeds child settings; no template identity or runtime template routes exist. Definition waiting JSON contains only type/mode/config/action, without runtime cursor/generation/diagnostics. It must be a once return/resume wait; nested create_task actions are rejected. Children copy the definition at event acceptance, retain `source_task_id` as provenance, and do not inherit subsequent edits. Trigger and child settings use one version-checked SetTaskPolling transaction. Source on/off uses the existing move operation.

Child title/description formats take precedence over event labels; supported placeholders use `{{key}}`. Replacement is one pass, and JSON substitution changes string values only. Source/resume prompts equal configured text after one-pass rendering, with no forced context appendix. Polling facts remain in task_events. New child titles are always prefixed with the current source title; cron inserts YYYY-MM-DD HH:mm [Timezone] after the source prefix and before an optional child title. The timestamp is the scheduled occurrence in the configured source timezone, not acceptance time. Legacy scheduled-title filler is omitted.

Composition calls `Service.SetExecutionDefaults(model.TaskExecutionSettings)` with current launch defaults and `Service.SetPollingValidator(func(model.TaskPolling) error)` with the pure typed poller validator. Defaults are copied when task/source child settings are saved; later changes do not change pending requests. Nullable external request `*string` permission fields preserve legacy fallback, while board requests require explicit permissions and obey the source initial launch policy; continuations always require manual Start. The typed validator also validates resolved child waiting settings inside the acceptance transaction; PR source child waits may use {{pr_id}}, {{login}} and {{author}} because those sources supply them. Cron child waits require explicit positive PR IDs and reviewer/author values when applicable; PR-only placeholders are rejected on save/create. Child waits are validated before persistence and again after event resolution.

Moving to Polling validates the runnable action. Resume waiting requires a linked thread and a nonempty continuation prompt. Inactive child waiting can be prepared before its initial request launches. Updates to active settings cannot clear required continuation data. Moving out of Polling, replacing waiting settings, or editing task settings advances generation. Rearming preserves the cursor; replacing PR/login/author/schedule identity resets it. Source definition edits affect future instances only.

`Store.ListDueTaskPolling(ctx, now time.Time, limit int) ([]model.TaskPolling, error)` returns only due tasks in Polling. `Store.AcceptTaskPollingOutcome(ctx, outcome model.TaskPollingOutcome, approvalTopicID int64) (bool, error)` returns false for stale/disabled checks; true includes duplicate-only successful checks. `PollingEvent.Cursor` initializes a created child’s baseline. Error outcomes update attempt/error/scheduling diagnostics only, without advancing cursor or accepting partial events.

`Store.BootstrapTaskSource(ctx, model.TaskSourceImport) (*model.Task, error)` atomically seeds a source with its owned child definition and links legacy request IDs to imported cards and event barriers. Import Key is a durable once-only marker; Column defaults Polling and may be TODO for paused imports. LegacyTaskImport carries cycle SourceKey, EventKey, RequestIDs, optional Variables, Polling, Cursor, Title and SourceURL. Adapters select event identities matching their new checker. Existing request prompt/policy/settings stay unchanged. Repeated import preserves local edits. `ListTrackedTaskThreadIDs(ctx) ([]string,error)` supplies the shared snapshot producer's board target set.

Daemon MoveTask runs under the same claim/dispatch mutex. It dismisses pending/starting/definitely failed requests with empty result thread/turn, and expires their callbacks. Started and ambiguous requests remain untouched. Claim/Retry reject board requests in TODO/Done. CompleteExternalLaunchRequest and receipt-confirmed ResolveExternalLaunchOutcome bind task.thread_id in the same transaction as the request result, enforce the target thread, and preserve the card column. Durable Sync receipts now retain their confirmed turn_id for exact initial-request recovery.

Startup upgrades legacy create_task action references by copying the referenced template definition into action.child_definition and removing template_id, in one transaction. It never derives child settings from source.config or rewrites ordinary task configs/requests. Reopening preserves edited owned definitions. Existing source events supply source_task_id provenance. Legacy template storage remains inert; /v1/task-templates routes return 404.

Source polling.action.initial_launch is optional `{mode:"manual"|"trusted_authors"|"auto", authors?:string[]}`. Missing policy is manual. trusted_authors is valid only for PR sources; normalized login matching is case-insensitive and ignores a leading @. Initial authorization uses the actual observed PR author; unknown authors require manual Start. A card must be visible before automatic claim. This policy is distinct from execution.approvals_reviewer and is saved atomically with the source trigger/child definition. It affects new requests only. Ordinary/child waiting actions reject initial_launch, and request validation rejects automatic continuations.

Task.source_author is read-only provenance, populated when a source event creates the task. Initial cards store the source name in request Source and actual author in Sender; continuations prefer the current snapshot author, then persisted source_author, and resolve Source through source_task_id. Source identity linkage is independent of these human display labels.

Bootstrap has a once-only source launch upgrade marker per imported source. It renames exact default Assigned PRs on the arcanum_review source to PR review and fills a missing review launch policy from configured legacy trusted authors. Explicit policy and custom names are preserved. Feedback/existing cron policy and all frozen requests remain untouched; new cron imports retain configured launch_policy. Later configuration edits do not replace UI settings. The upgrade can backfill author from accepted event facts/actual legacy PR Sender. It does not rename historical child tasks.

## Task ordering and drag moves

`MoveTaskInput` accepts optional `before_task_id`. A nonempty ID inserts immediately before that card in the target column; an empty string appends. Omitting the field preserves the older explicit `position` contract. Neighbor insertion validates the moved card's expected version and the anchor's current column and card kind (source versus ordinary task). Missing/moved/self anchors return 409; incompatible card kinds return 400. Cross-column Polling readiness and the launch cancellation gate still apply.

Within a column, order is `(position, id)`. Neighbor insertion atomically rebalances destination positions to spaced integers, including legacy equal positions. Other cards keep their relative order, editable versions, settings, polling generation and requests. Same-column reorder increments only the moved task's version and records a `reordered` event; it does not revalidate/rearm polling or cancel requests in TODO/Done.

The browser previews insertion at card midpoints with a dashed placeholder of the grabbed card's height. The original is dimmed and marked Moving. Drop updates the visible order immediately and shows Saving position until the returned Task settles the move. SSE/focus/periodic refreshes are deferred during dragging or saving; old in-flight snapshots are discarded, then reconciliation resumes. Failures restore the previous order, retain an actionable error and refetch. Drag end and Escape remove the preview; Escape also rejects a later native drop from that gesture. Saving does not await the full-board GET.

## Compact board reads and reorder-only command

`GET /v1/task-cards` returns `TaskCardDTO[]` (empty list is `[]`). It contains task identity, display text, column/position/version and provenance; execution has only last_seen_turn_status/last_seen_thread_status/last_poll_at; requests have only id/status; polling has type/mode/action.type, check timestamps/error and `problem` (empty means configured readiness passed). Config, prompts, child definitions, cursor, execution settings and full snapshots are omitted. `GET /v1/tasks/{id}` remains the full detail read; the legacy task list remains compatible. SSE reconciliation hashes compact cards.

`POST /v1/tasks/{id}/reorder` uses expected_version, column and before_task_id (empty appends) and returns a compact card. The current column must equal the requested column inside the same transaction; otherwise 409, with no changes. The version check and neighbor/category validation apply as for MoveTask. This command does not run polling readiness checks, rearm polling, cancel requests or acquire the Sync/launch gates. The browser uses it for same-column drag; cross-column transfers use `/move` and preserve their launch cancellation guard.

## Priority and attaching existing chats

Task and TaskCardDTO include `priority`: low, normal or high. Create may omit it (normal). Task PATCH may omit it (preserve existing) or provide a valid value; empty/unknown values are invalid. Priority does not reorder cards. Fresh and upgraded tasks default to normal, including newly generated source children.

`POST /v1/tasks/{id}/chat` takes `{expected_version, thread_id}` and returns the same full Task. A positive version is required. Missing task returns404; sources/empty IDs are invalid; stale version, different existing binding, another task owning the chat, active/uncertain launch or conflicting historical launch chat return409. Same binding is idempotent at the current version. The daemon reads chat authority without resume/start and rejects missing/wrong/failing reads before binding; authority errors propagate without a database mutation. Link increments task version and polling generation, preserves config/column/cursor, records chat_linked and activates ordinary snapshot projection. No browser launch/approval operation is added.

`POST /v1/tasks/{id}/priority` takes `{expected_version, priority}` and returns a compact TaskCardDTO. A positive version and low/normal/high priority are required (400); a missing task returns404 and a stale version returns409. The transaction updates only priority, version and updated_at and records priority_changed. Ordering, configuration, polling generation/cursor/timestamps and launch requests remain unchanged. The command never enters Sync or launch gates. This lets a card change priority without loading full task details.

Task and TaskCardDTO include ticket_url (empty means unlinked). Create defaults to empty; optional task PATCH preserves the current value when omitted. `POST /v1/tasks/{id}/ticket` accepts `{expected_version, ticket_url}` and returns a compact TaskCardDTO. Positive version and an empty string, tracker key or absolute HTTP(S) URL without credentials are required (400); omitted/null ticket_url is rejected rather than clearing the link. Missing task returns404 and stale version returns409. The command changes only ticket_url, version and updated_at and records ticket_link_changed; it preserves source_url, chat binding, order, settings, polling runtime and launch requests. URLs are stored/displayed only; no external tracker API is called.

A short tracker key (for example TASK-123) is stored as its full HTTPS URL on st.yandex-team.ru by create, optional task PATCH and POST ticket. Ticket_url remains a full URL in full/compact responses. Empty still clears; a missing or null command field is still invalid.

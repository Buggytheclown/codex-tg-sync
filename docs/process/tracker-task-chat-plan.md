# План создания Task из Трекера и именования чатов

13 ноября 2026. Основания — [спецификация](tracker-task-chat-spec.md) и [её проверка](tracker-task-chat-spec-review.md). База кода — `346d474`. Документ описывает будущие изменения.

## 1. Создать Task по ключу или ссылке

Минимальное полезное приращение заканчивается сохранённой Task в TODO. В `NewTask` добавить поле тикета выше заголовка для типа Task. Само сохранение использует существующий `POST /v1/tasks` с `title` и `ticket_url` в одном запросе. Тип PR использует свою форму. Ввод и поиск никогда сами не создают карточку. Защитить submit от второго клика, при неопределённом ответе сначала перечитать доску. У существующего POST каждый вызов создаёт новый ID, поэтому прозрачный повтор записи опасен. Одинаковый тикет сам по себе не доказывает повтор операции.

Отдельное loopback-действие `POST /v1/tracker/lookup` принимает ключ либо ссылку и возвращает только `key`, `summary`, `url`. Применить существующие Host/Origin и JSON-проверки доски. Для lookup разрешить короткий ключ и HTTPS URL известного хоста Трекера с путём тикета, нормализовать регистр, отбросить query и fragment. Сохранение старых произвольных ссылок продолжает следовать текущему контракту. Исполнитель Трекера вызывает проверенный `get_issue` с полями ключа и названия и нулём комментариев через серверный `ya tool mcp connect tracker`. Аргументы передавать массивом, ключ отдельно, исполняемый файл искать в подготовленном окружении службы. Проверять процесс, RPC error, `isError`, наличие полей и совпадение ключа. Ограничить время и размер ответа, не возвращать браузеру stdout, описание тикета или сведения авторизации. Вызов от имени launchd проверить одним read-only чтением до интеграции UI. Ошибка должна оставлять доступным ручной ввод.

В форме помнить, для какого ключа подставлен заголовок и редактировал ли его пользователь. Распознавать завершённый ввод при вставке или подтверждении поля, объединять обращения для одного ввода. Это исключает чтения последовательных ключей при наборе цифр. Брать результат только для открытой формы, текущего ключа и поля, допускающего автозаполнение. При смене ключа сразу убрать устаревший автозаголовок. При ручном названии сохранить его. Повтор чтения после ошибки явный. Проверить key/URL, две смены ключа с обратным порядком ответов, ручную правку во время запроса, очистку, переключение типа, 403/404, недоступный процесс, сохранение без тикета и отсутствие вызовов при регулярной загрузке доски. ## 2. Создать, привязать и открыть чат разработки без хода

**Настройки.** Добавить в локальный `config.env` два шаблона с начальными значениями `ПР {ticket} {title}` и `Фикс {ticket} {title}`, настройку каталога для чата с наследованием `CTR_GO_DEFAULT_CWD` и настройку модели чата доски. Личный путь к agents и выбранный ID модели задаются при установке. Если модель не указана, взять модель по умолчанию из каталога App Server. Образец конфига содержит только примеры. Достаточна подстановка двух литеральных полей за один проход. Сохранять скобки и внутренние пробелы самого названия. Неизвестные поля шаблона и пустой результат давать как понятную ошибку настройки соответствующей функции. Для Task без тикета предлагается опустить ключ и разделяющий пробел.

**Контракт.** Добавить защищённую команду доски `POST /v1/tasks/{id}/create-chat` с `expected_version` и ID попытки, стабильным при повторе. Ответ содержит идентификаторы Task и чата, состояние операции и признак первого успешного создания для UI. В деталях Task доступны состояние неопределённого исхода, восстановления привязки и повтора именования. Использовать существующий канал обновлений доски. Для PR, Source, Schedule и занятых привязок запуск отклоняется. Режим работы Telegram Sync и видимость доски не служат условием создания пустого чата при доступном общем App Server.

**Сохранение и RPC.** В SQLite добавить узкую запись операции на Task с уникальным ID попытки, стадией, замороженными настройками и именем, известным ID чата и краткой категорией ошибки. Старые карточки изначально не имеют записи. Сначала сверить текущую версию, привязку, каталог и модель. Для явно заданной модели пройти каталог до совпадения или конца, включая поддерживаемые скрытые модели, если они настроены. У текущего `ModelList` выдача ограничена первой страницей. Ошибка чтения каталога допускает повтор. Перед созданием сверить локальные условия ещё раз и атомарно закрепить единственную попытку на Task. Ветка повтора собственной операции проверяется до отклонения устаревшей версии. Другая вкладка получает текущее состояние этой Task.

1. Задействовать существующий менеджер авторитетного writer и его резервирование до появления ID. Записать стадию отправки перед единственным `thread/start` с разрешёнными настройками, cwd и model. Для этого расширить `control.ThreadStartOptions` опциональной моделью. Прежние вызывающие пути при пустом значении сохраняют свой запрос. Из ответа извлечь и немедленно записать любой валидный ID, даже если другие поля неожиданны. Затем выполнить ClaimThread для полученного ID и проверить возвращённые cwd и модель. При несовпадении сохранить ID и показать причину.
2. Привязку проводить теми же проверками уникальности, истории запусков и смены поколения, что и `LinkTaskChat`. Сериализовать локальные решения с ручной привязкой и выдачей конкурирующих запусков, учитывая запись операции также на этих путях. Не удерживать общую блокировку или SQLite-транзакцию во время сетевого IO. При конфликте показать известный ID и причину. Чужая новая привязка имеет приоритет перед запоздалым ответом.
3. Присвоить имя через `thread/name/set` до первого открытия, проверить результат, отпустить writer. Завершение этой команды оставляет историю пустой. Текущий внешний dispatcher после `RecordExternalThread` начинает первый ход. Поэтому для Task нужен отдельный короткий путь с переиспользованием транспорта и владения writer. Проверить отсутствие `turn/start`, запусков в очереди и зависшей резервации на всех исходах.
4. После рестарта запись с известным ID позволяет закончить привязку или именование того же чата. Стадия возможной отправки без сохранённого ID означает неопределённый исход. Показать его в UI и дать привязать найденный чат через существующую форму. В транзакции успешной ручной привязки завершить запись unknown и снять резервирование. Пока RPC выполняется, ручная замена ждёт определения исхода. Если ID не удалось записать и процесс ещё жив, вернуть его как доступное пользователю средство восстановления. Уверенный отказ до отправки разрешает новую попытку. Разрыв связи не доказывает отказ.
5. UI открывает созданный чат по `codex://threads/<id>?prompt=<URL-encoded ticket URL>` только в результате первоначальной команды. После потери ответа, восстановления, повторного клика или при существующей связи использовать обычный deep link. Оставить видимую ссылку для явного открытия после запрета браузером и действие «Скопировать ссылку на тикет». При отсутствии тикета открывать пустой ввод. Параметры модели, пути и шаблона берутся из конфигурации сервиса.

**Приёмка.** Две вкладки, двойной клик, ошибка записи после выдачи ID, рестарт до и после записи ID, потерянный HTTP-ответ, смена привязки во время RPC, занятый writer, неверный каталог, неизвестная модель. Считать физические `thread/start` и `turn/start`. На изолированном профиле открыть созданный чат из реального браузера, сверить cwd и модель, дописать текст и закрыть без отправки, открыть снова и проверить сохранность текста. Отдельно проверить, что при ручной отправке возникает ровно один первый ход. ## 3. Дать имя чату fix при наличии родительской Task

Использовать факт первого запуска от feedback-источника. Для идентичности нужны исходное polling-событие, тип source или его устойчивый ключ, точная PR-карточка и созданный для неё thread ID. Название source на экране настраивается. Продолжение с `target_thread_id`, импорт исторических карточек или повторное обнаружение канонического ПРа не создают запрос на переименование. Источники assigned review и ручные привязки исключаются.

В момент подтверждённой первой привязки создать запись об ожидающем именовании для пары PR-карточка/чат. Использовать транзакцию, где подтверждена привязка. Обработать повтор после частично выполненного `RecordExternalThread`, включая случай уже записанного ID. При появлении родителя или тикета после запуска (через действие ticket или общий PATCH) повторно рассматривать только ожидающие записи затронутой Task. Если родитель и тикет существовали раньше, обработку инициирует сама привязка чата. После рестарта выбрать незавершённые записи. Ранее существовавшие чаты массовой обработке не подлежат. Итоговое имя всегда строится из текущих данных родителя.

При известном родителе перед первым ходом сделать ограниченную по времени попытку именования нового пустого чата. Она нужна до автоматического заголовка Desktop. Ошибка оставляет ожидающую запись и допускает запуск хода. Последующую обработку выполняет существующий reconciler. Перед RPC перепроверить ID чата, родителя, тикет, владельца writer и текущее фактическое имя. Смена связей делает устаревшую работу недействительной. Применённое имя записывается один раз. При неопределённом ответе сначала прочитать имя по тому же ID. Совпадение с целевым завершает операцию. Ошибка имени даёт действие повтора на карточке, без повторной отправки промпта. Если родитель сменился после успешного именования, новое название можно применить явно.

**Поздняя привязка.** Согласованное правило для уже заданного имени неизвестного происхождения — показать целевое имя и «Применить шаблон». Пустое фактическое имя допускает автоматическое присвоение. Проверить сырое поле имени, поскольку отображаемый заголовок имеет fallback. У RPC нет атомарной проверки предыдущего имени. Повторное чтение сужает окно гонки с Desktop, но не даёт строгой гарантии в момент одновременной записи. Если имя уже совпадает с шаблоном, завершить операцию без записи.

**Приёмка.** Прогнать оба порядка появления родителя и чата, позднее добавление тикета, явно названный чат, второй раунд замечаний, замену чата, другой source для того же ПРа, сбой/повтор RPC и рестарт. Наблюдать имя в самом Codex. Должны сохраниться исходная Task, её чат, подтверждение и количество запусков фикса. ## Порядок выпуска

Каждый этап начинается с проверки через его обычную точку входа. Первый можно выпустить отдельно. Этап 3 использует настройку шаблонов и RPC именования из этапа 2. Новые таблицы или поля добавляются без реконструкции истории существующих карточек. Проверить создание БД с нуля, обновление со старой схемы и повторное открытие. Обновить справку по конфигу, контракт доски, ADR-035 и карту регрессий одновременно с изменением поведения.

Перед выпуском выполнить `go test ./...`, targeted `go test -race` для storage, daemon и appserver, `go build -buildvcs=false ./...`, в ui — `npm test` и `npm run build`. Независимое ревью и проверка публичного diff входят в обычный процесс проекта. Сквозной прогон использовать для названия окна, черновика, реальной модели и запроса запуска фикса. Для проверки годятся тестовые карточки и изолированный запуск. Итоги живых проверок фиксировать отдельно от результатов модульных тестов.

# Идентичность срабатывания крона

Статус: требования и политика перехода согласованы в обсуждении 2026-11-03.
Реализация выполнена; проверки и состояние установки фиксируются при передаче
результата. Открытых продуктовых вопросов нет.

## Проблема и цель

Сейчас дедупликация крон-событий учитывает задачу, правило и локальную дату,
но теряет время по расписанию. После выполненного запуска в 13:00 перенос
расписания на 16:00 того же дня подавляет новое срабатывание как дубликат.

Нужно различать конкретные запланированные срабатывания крона, сохраняя защиту
от повторов одного срабатывания при опросах, перезапусках и повторном включении
поллинга. Изменение относится только к крону: ключи событий PR сохраняются.

## Согласованное поведение

1. Идентичность крон-события включает владельца расписания, идентичность правила
   там, где оно есть, и полные запланированные дату и время с однозначной
   временной зоной. Сравнивается конкретный момент времени; точный формат
   хранения определяется при проектировании.
2. Используется время, вычисленное из расписания, а не время очередной проверки,
   создания запроса или фактического запуска Codex. Проверки в 13:01 и 13:02
   одного слота 13:00 имеют одну идентичность.
3. Ежедневное расписание 13:00 работает как прежде: один запрос сегодня, новый
   запрос завтра. Перезапуск демона не создаёт повторный запрос за сегодня.
4. Если запуск 13:00 уже был принят, расписание изменено на 16:00, а задача
   снова находится в Polling, слот 16:00 того же дня может создать новый запрос.
   Для постоянно активного cron-source новый слот может создать новую дочернюю
   задачу. Дубликаты ни запросов, ни дочерних задач не допускаются.
5. Редактирование промпта, режима подтверждения, прочих настроек или повторный
   вход в Polling не создают новую идентичность того же слота. Перенос 13:00 →
   16:00 → 13:00 не разрешает повторить уже принятое срабатывание 13:00.
6. Принятый запрос сохраняет защиту от дублей независимо от его состояния:
   ожидает подтверждения, выполняется, завершён, отклонён или завершился ошибкой.
   Существующие явные механизмы повторной попытки сохраняются.

## Ограничения

- Сохраняются поддерживаемые расписания, вычисление текущего слота, поведение
  после сна/перезапуска и ограничение опоздания max_lateness. Изменение ключа
  не разрешает запуск после истечения этого ограничения и не воспроизводит
  пропущенные периоды.
- Поддержка нескольких времён в одном cron-выражении не добавляется: исправляется
  идентичность уже вычисляемого срабатывания, в том числе при переносе расписания.
- Задачи исполняют правила только в Polling. Выход из Polling, выбор Then,
  подтверждение в Telegram, привязка чата и возврат результата в Inbox сохраняют
  существующее поведение. Автоматическое повторное включение поллинга не добавляется.
- Существующие запросы, история, дочерние задачи и привязанные чаты сохраняются.
  Замена ключа не должна сама по себе запускать Codex или менять колонки.
- Новый запуск и принятие его события остаются атомарными: ошибка записи не
  оставляет частично созданный запрос или дочернюю задачу; следующая проверка
  может безопасно повторить принятие.
- Не требуется изменение UI, дополнительный планировщик или очередь запусков.

## Переход со старых ключей

В текущих polling_event уже сохраняется scheduled_at. При наличии достоверного
времени старого события оно должно защищать тот же слот от повторного запуска
после обновления, разрешая другое время того же дня. Время создания запроса
не заменяет scheduled_at: запуск мог быть создан с опозданием.

В старом импорте cron встречаются записи только с датой, без scheduled_at.
Восстанавливать их время из нынешнего расписания нельзя: расписание могло
измениться. По решению пользователя для такой неоднозначной записи сохраняется
прежняя защита на всю её дату: новое время в эту дату тоже не создаёт повторный
запуск. Защита не переносится на последующие даты. Для независимых правил и
задач сохраняется их собственная область дедупликации.

Повторное обновление или прерванный переход не должны терять защиту от дублей,
создавать запросы или менять сохранённые промпты.

## Приёмка

- [x] Ежедневный слот 13:00 создаёт один запрос при нескольких опросах и после
  перезапуска; следующий день создаёт следующий запрос.
- [x] После принятого слота 13:00 перенос на 16:00 того же дня создаёт ровно
  один новый запрос при активном поллинге и в пределах допуска опоздания.
- [x] Возврат расписания на уже принятые 13:00, редактирование промпта и
  повторное включение поллинга не дублируют слот.
- [x] Обычное правило задачи и повторяющийся cron-source одинаково защищены;
  у source не появляются повторные дочерние задачи за один слот.
- [x] При переходе старое событие с известным scheduled_at не воспроизводится;
  другое время той же даты разрешено. Запись без времени защищает всю свою
  дату, включая изменённое время, но не следующую дату; повторный/прерванный
  переход сохраняет эту защиту.
- [x] Сохраняются временная зона, прежнее вычисление слота, допуск опоздания,
  поведение после сна и отсутствие запуска вне Polling.
- [x] Ошибка записи и повторная обработка не создают частичных результатов
  или дубликатов; существующие запросы и привязки сохраняются.
- [x] Ключи и поведение событий PR не изменились.

## Основания по текущему коду

- internal/polling/checker.go: ключ крона содержит запланированный slot в UTC
  RFC3339; payload сохраняет scheduled_at с временным смещением.
- internal/polling/rules.go: независимые правила разделяются стабильным rule ID.
- internal/storage/store_task_outcomes.go: принятые события дедуплицируются в БД;
  создание запроса/дочерней задачи и принятие события выполняются транзакционно.
- cmd/ctr-go/board.go и internal/storage/store_task_import.go: старые запросы
  импортируются по ключу с датой, без обязательного сохранённого времени слота.
- ADR-030 сохраняет исторический контракт, новое дополнение ADR-035 описывает
  идентичность по времени и совместимость со старыми ключами.
- internal/storage/store_cron_identity.go: совместимость проверяется при принятии
  события, без перезаписи истории, отдельной миграции или изменения схемы.

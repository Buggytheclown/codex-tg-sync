# Проверка плана Task / PR / Schedule

Дата: 2026-11-11. Проверены спецификация, план и исходный код; приложение,
живые данные и Telegram не изменялись. Тесты приложения не запускались.

## Независимая проверка

Reviewer получил ревизию 1 плана, цель, ограничения и первичные исходники,
без подсказки выводов автора. SHA-256 проверенной ревизии 1:
`634cc1913343787d9f1baab22e93e23b3584200c552152d20492c1635051d885`.

Ниже реальные результаты этого ревью и изменения в ревизии 2. Замечания относятся
к плану, а не утверждают, что новая функциональность уже реализована.

## Найденные дефекты исходного плана

### P1: несуществующая защита замены PR

Ревизия 1, раздел 3, предполагала существующие daemon-защиты при замене PR ID.
На деле `internal/daemon/board.go:UpdateTask` делегирует storage без таких guards,
а `internal/storage/store_tasks.go:UpdateTask` не отвергает pending/uncertain
launch. Аналогичная защита есть у `LinkTaskChat`, но она не вызывается PR edit.

Сценарий: frozen request для PR A ждёт Telegram approval; ссылка и rules меняются
на B; аппрув запускает работу по A у карточки B. Обычного version check недостаточно:
request уже сохранён и не зависит от нового editable config.

В ревизии 2 добавлены НОВЫЕ guards смены номера ручного PR: authoritative chat
read, launch gate, повторная проверка version/identity/незавершённых requests и
атомарный update. Прямой PATCH и combined workflow обязаны иметь одну защиту.
Same-ID URL edit не требует лишнего App Server IO. Добавлены проверки гонки
claim/update и отказа без частичного изменения ссылки, rules или request.

### P2: новый PR ID при прежнем source key

Ревизия 1 одновременно разрешала смену номера и сохраняла source provenance.
В `internal/polling/checker.go` PR-source key содержит PR ID;
`internal/storage/store_task_outcomes.go` находит существующий результат по нему.
После A → B ключ A продолжал бы ссылаться на B. Повторное discovery A давало
бы противоречащие source-key/PR-ID результаты и конфликт всего source pass.

В ревизии 2 у PR с PR-source provenance номер неизменяем. Другой формат URL
того же ПРа разрешён; другой ПР создаётся/выбирается отдельной карточкой.
Новый alias registry или переписывание исторического source identity не нужны.
Добавлен тест повторного discovery после отклонённой смены номера.

## Решение миграции — подтверждено

После технического ревью пользователь выбрал сохранение прямых PR-ссылок старых
ручных Task в History с очисткой активного поля. Связи остаются ручными.
Решение внесено в ревизию 3 плана, спецификацию и частную карту; gate закрыт.

Reviewer также потребовал определить передачу private versioned input до startup
backfill. В ревизии 2 описаны отдельные offline dry-run/apply, read-only preflight
обычного старта, проверка digest полного набора/версий внутри apply и marker.
Это исключает применение generic migration раньше решений карты.

Выбранный общий backfill покрывает и отдельно согласованную ручную отвязку.
Индивидуальные migration commands для связывания убраны: частная карта
остаётся отчётом и предложениями для ручной линковки.

## Сравнение альтернатив

- Один parent ID вместо общей subtask/relation модели соответствует кардинальности;
  строки из общего compact snapshot убирают отдельную синхронизацию копий.
- Пассивный metadata worker/cache сохраняет guard «действия только в Polling».
  Полный snapshot ради footer дороже из-за комментариев; stale metadata cache
  для правил менял бы их семантику. Ни то, ни другое не требуется.
- Канонический UNIQUE PR ID расширяет существующую дедупликацию, сохраняя
  event/request guards. Source aliases для этой задачи не оправданы.
- SQLite rebuild необходим из-за CHECK колонок. Сохранение event rowids нужно
  существующему ownership ручных перемещений; переписывание событий не нужно.
- Дополнительно при авторской проверке уточнено: Task теряет PR-привязку,
  но generic source URL сохраняется; согласование не разрешало терять этот контекст.

## Ограничения и будущая валидация

Проверка основана на коде, ADR-035/регрессионной карте и согласованных сценариях,
а не на выполненной реализации. Словарь raw Arc statuses требует ограниченной
read-only проверки перед UI mapping; существующие API-команды уже используются
в приложении. Приложение/миграция должны пройти тесты и live QA из раздела 8
плана при реализации. Сейчас проверены только документы и отсутствие известных
частных идентификаторов в добавленных публичных материалах.

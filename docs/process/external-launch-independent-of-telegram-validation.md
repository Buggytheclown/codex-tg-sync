# Проверка независимого запуска Codex

Дата: 2026-11-09. Проверены
[требования](external-launch-independent-of-telegram-spec.md),
[план](external-launch-independent-of-telegram-plan.md) и
[контракт ADR-037](../adr/ADR-037-independent-external-execution.md).

Реализация находится в рабочем diff. Установка, перезапуск рабочего демона,
коммит и публикация в эту проверку не входят. Сторонние изменения cron, task cards,
UI и их документации в общей рабочей копии сохранены отдельно от этой задачи.

## Подтверждённый результат

- Принятый запуск непосредственно создаёт/возобновляет чат и запускает ход;
  Telegram IO не выполняется в этом пути. Продолжения сохраняют точный target,
  проверки idle и исходные параметры выполнения.
- Durable-фазы различают отсутствие отправки, неопределённый RPC и известные
  thread/turn ID. Повтор первого хода после подтверждённого отказа использует
  уже созданный чат. Сбой записи журнала запрещает RPC и даёт известный отказ.
- Ошибки Telegram не меняют execution outcome. Исходная карточка получает
  отдельный Telegram Retry, в том числе после завершения Codex. Повтор callback
  не создаёт следующую попытку; неизвестные предшественники остаются в истории.
- Подтверждение старой попытки не заменяет активную привязку. Сопоставление
  имён сохраняет legacy/ambiguity fences. История Retry не блокирует обычное
  восстановление отображения после истечения уже известного топика.
- Наблюдение за выполнением и cleanup не зависят от renderer. Есть проверки
  зависшего Telegram-редактирования, позднего хода, detached/off, ошибок записи
  terminal и закрытого неизвестного запроса с известным живому lease turn ID.

## Автоматическая проверка

Полный свежий прогон: `go test -p 1 ./... -count=1` — прошёл.
Адресный `go test -race ./internal/daemon ./internal/storage -run 'Test(External|DispatchExternal|BoardContinuation|BoardInitialLaunch|Topic|SyncOff|Detached|PresentationWait|KnownLegacy|LegacyNormalization|BindingMessage|ClosingUnknown|CompletedExternal)' -count=1` — прошёл в обоих пакетах.
Сборка: `go build -buildvcs=false ./...` — прошла.
`git diff --check` — прошёл. Python readback helper проверен через `ast.parse`.
Добавленные строки проверены на приватные абсолютные пути, реальные Bot API
credentials и приватные ключи; совпадений нет. Полный предусмотренный AGENTS
поиск секретных ключевых слов также выполнен: это поиск мест хранения/обработки,
а не утверждение об отсутствии таких слов в исходниках.

Адресные проверки покрывают все AC-01–AC-08. Отдельно проверены:

- фактическое отсутствие Telegram-вызовов из принятого dispatch;
- SQLite failure перед RPC и после подтверждения turn;
- восстановление каждой фазы после открытия БД заново;
- повтор callback и сохранение unknown после перезапуска;
- поздняя materialization после нормализации legacy alias;
- перенос задачи во время ожидания thread/start с сохранением чата и отменой
  ещё не отправленного первого хода;
- невозможность принять посторонний latest turn за неизвестный запуск;
- невозможность оживить истёкший approval route при позднем завершении отправки;
- освобождение старого writer после более позднего хода без рестарта,
  включая зависший renderer и отключённый Sync;
- сохранение одноразовой политики launch-topic 429 для быстро завершившейся работы.

В ходе проверки обнаружены и устранены замечания ревью о отмене во время
thread/start, повторной активации approval routes, terminal persistence fence,
legacy aliases, гонке нормализации/materialization и зависимости supersession
cleanup от renderer. После исправлений проверка в свежем контексте не нашла
оставшихся существенных блокеров; новый blocked-renderer fixture прошёл.

Один полный прогон, запущенный одновременно со сборкой race-тестов, упёрся
в существующий пятисекундный deadline `TestStartConcurrentCallsShareInitializedProcess`.
Также встречались непостоянные падения неизменённых poller-health fixtures;
их отдельный прогон на исходном HEAD (20 повторов) прошёл. Финальный полный
прогон выполнен последовательно по пакетам и прошёл без исключения тестов.
Сами эти сторонние проверки и их временные ограничения не менялись.

## Живая проверка

`TestLiveExternalLaunchTelegramRetry` прошёл на настоящем shared App Server
и настроенной приватной Telegram-группе. Использовались отдельная временная БД,
собственная launch-карточка и ephemeral Codex-чат с безвредным prompt без tools.
Рабочий демон не перезапускался, второй потребитель `getUpdates` не запускался.

1. App Server подтвердил один созданный чат и один ход до первой попытки
   создать топик. Настоящие события завершения и `thread/read` metadata
   подтвердили тот же turn и ожидаемый Final.
2. Telegram реально создал первый топик, но тест скрыл успешный ответ
   от обработчика. Карточка завершённой работы получила Telegram Retry.
3. Обработан актуальный callback исходной карточки. Создан один новый топик,
   восстановлены User/Status/Final. Счётчики thread/start и turn/start остались 1.
4. Отдельный аутентифицированный Telegram-клиент прочитал исходную карточку:
   Completed, Telegram connected, Retry убран. В восстановленном топике прочитан
   настоящий ожидаемый Final. Это readback, а не только успех Bot API.
5. Оба собственных тестовых топика и launch-карточка удалены; ephemeral-чат
   и клиентские соединения освобождены.

Для повторения opt-in тест требует `CODEX_TG_EXTERNAL_LIVE=1`, путь к
`tests/probes/external_launch_readback.py` в `CODEX_TG_PROBE_READBACK` и каталог
уже авторизованного `telegram_client` в `TELEGRAM_CLIENT_MODULE_DIR`.
Секреты берутся из локальной конфигурации и существующей Telegram-сессии,
в репозитории они не хранятся.

## Исправление после установки

При первом обновлении обнаружена регрессия: сброс `telegram_rendered_status`
при startup repaint поставил в очередь старые terminal-уведомления, для которых
в legacy-БД отсутствовала запись delivery ledger. Задачи повторно не запускались.
Исправление сохраняет rendered execution status при сбросе projection fingerprint
и не создаёт terminal notice для уже показанного статуса.

`TestLegacyCompletedCardRefreshDoesNotBackfillTerminalNotice` воспроизводит
проблему после физического удаления новых столбцов и открытия старой схемы:
до исправления возникает лишнее сообщение, после исправления карточка обновляется
без него. Существующий тест настоящего завершения сохраняет одно уведомление.
В изолированном release checkout прошли полный `go test -p 1 ./... -count=1`,
адресный `-race`, `go build -buildvcs=false ./...`, проверка diff/секретов
и отдельное read-only ревью исправления.

Проверка установленного исправления подтвердила отсутствие новых terminal
deliveries после рестарта и сохранение Sync session. Authenticated Telegram
readback также не обнаружил новых terminal notices. Эта проверка выявила
повторные edit-запросы при ответе Telegram `message is not modified`:
адаптер теперь принимает такой ответ 400 как подтверждение уже доставленного
содержимого. `TestBotUnchangedMessageEditIsDelivered` проверяет обычное
и entity-rendered редактирование, отсутствие лишнего fallback и сохранение
ошибки для действительно отсутствующего сообщения; до исправления тест падал.

## Граница вывода

Live probe использует ephemeral-чат и события App Server:
историю ephemeral-чатов API не предоставляет. Подмена неизвестного подтверждения
событием и все варианты поздних конфликтующих событий проверены локальными
storage-тестами; живая проверка не подключала второй update consumer рабочего бота.

# Sync: освобождать подписки простаивающих чатов

Статус: реализовано и проверено автоматическими тестами в рабочем дереве. Дата: 2026-11-01.

## Цель и границы

Существование Telegram-топика не должно загружать Codex-чат и удерживать его MCP.
Sync читает простаивающие чаты без resume, временно подписывается на необходимую
активную работу и явно освобождает собственные подписки. Сохраняются prompt,
steer, stop, approvals/input, продолжения, доставка Final и восстановление.

Не меняются схема БД, настройки частоты, Telegram-команды, протокол владения
writer, MCP-конфигурация, yadebug и версии зависимостей. Это отдельное исправление
жизненного цикла codex-tg, без перехода на HTTP MCP или Playwright CLI.

## Основания

- `internal/daemon/sync.go::reconcileSyncLocked` вызывает
  `subscribeSyncThreadLocked` для каждого подключённого топика до чтения состояния.
- `subscribeSyncThreadLocked` делает `ThreadResume` один раз на poll generation;
  обратного RPC нет. `syncSubscribedThreads` очищается при смене транспорта,
  но не при завершении хода или удалении топика.
- `Client.ThreadReadLatest{,Summary}` уже читает metadata и только последний ход
  через `thread/read` + `thread/turns/list`; этот путь не требует resume.
- Writer использует другое соединение. `WriterManager.MarkTerminal` закрывает его,
  только когда завершены все его операции; поэтому один завершённый чат может
  удерживаться до конца другого долгого хода.
- ADR-032 сохраняет историю при очистке представления; ADR-034 уже определяет
  единственную проекцию, dirty-worker и периодическую сверку. Их переиспользуем.
- [Контракт App Server](https://learn.chatgpt.com/docs/app-server#unsubscribe-from-a-thread):
  отписка относится к текущему соединению. После последнего подписчика выгрузка
  ожидает 30 минут без активности; чужая подписка может продолжать удержание.
- Изолированные проверки Codex 0.166.0 подтвердили запуск MCP при загрузке чатов
  без использования инструментов и корректную очистку при штатном shutdown.
  Долговременная выгрузка после grace period ещё не проверена.

## Архитектура

Остаются два существующих соединения: poll для наблюдения и writer для команд.
Подписки принадлежат соединению; топики и writer leases остаются отдельными
понятиями. Новые фоновые циклы и универсальный менеджер подписок не нужны.

| Сценарий | Чтение | Подписка |
| --- | --- | --- |
| Простой, завершённый или ещё не загруженный чат | poll, metadata + последний ход | отсутствует |
| Desktop-ход выполняется или ждёт input/approval | poll; важные события будят dirty-worker | poll после подтверждения активности |
| Telegram prompt/steer или external continuation | writer под действующим lease | writer после resume/start |
| Terminal подтверждён и проекция сохранена | доставка из сохранённой проекции | собственные подписки освобождаются |
| Чтение не удалось, состояние неоднозначно | существующее восстановление | ошибку не считать завершением; новую подписку вслепую не создавать |

### Poll: сначала прочитать, затем решить

Перенести безусловный resume из начала `reconcileSyncLocked` за успешное
авторитетное чтение. Не определять активность по наличию топика или возрасту PID.
Переиспользовать `terminalGateSnapshotNeedsHotPolling` и существующие проверки
локальных starting/active/unknown leases; не создавать параллельную классификацию
статусов. Для решения использовать свежий snapshot до sticky-merge старых данных.

Для активного внешнего хода подписаться один раз в текущем poll generation,
затем выполнить catch-up через существующий dirty-worker. Это покрывает промежуток
между чтением и подпиской; события продолжают только инвалидировать проекцию.
Сохранить 500 ms coalescing и запрет чтений на streaming deltas.

Если есть действующий writer lease, его соединение уже обслуживает ход:
дополнительная poll-подписка не нужна. Перед снятием уже существующей poll-подписки
убедиться, что writer успешно подключён; неоднозначный dispatch защищать как раньше.

Когда свежие данные доказывают простой и нет защищённой локальной операции,
отписать poll. Удалять запись из `syncSubscribedThreads` только после успешного
ответа. Ошибку сохранить для повторной сверки и штатной диагностики; не выдавать
её за успешное освобождение. Это же множество обеспечивает повторную попытку.

Чат, запущенный из desktop после простоя, обнаруживается текущим periodic sweep
или доступным глобальным событием. Не полагаться на событие от неподписанного
чата. Обычная задержка первого обнаружения — до настроенного интервала опроса
(по умолчанию 60 секунд), плюс чтение и доставка. Короткий ход, завершившийся между
опросами, всё равно проходит обычный catch-up последнего User/Status/Final.

### Writer: освобождать конкретный чат, сохраняя остальные

Входящие Telegram-команды и continuations сохраняют существующие resume,
writer-generation, receipts и проверки актуального хода. Resume не является
основанием создавать ещё один MCP, если чат уже загружен, и не заменяет ownership.

После успешного сохранения terminal-проекции явно отписать завершённый thread
на `lease.Process`; затем сохранить существующее освобождение lease. Не ждать
успешной отправки всех Telegram-частей: повтор доставки идёт из БД.
Подключить одинаковую очистку к обычному terminal, board continuation и известным
abort-путям, на которых чат уже был загружен, но новая работа точно не отправлена.
Не освобождать подписку при неизвестном исходе dispatch или ожидании ответа.

Ошибка отписки не должна удерживать финал или превращать завершённый ход в active.
Для writer оставить небольшую in-memory карту неудачных отписок с thread ID,
Process и generation из существующего lease. Повторять в текущем reconcile,
без отдельного worker/таймера. После подтверждённого закрытия соответствующего
соединения запись больше не нужна.

Перед повтором проверить актуальную generation и отсутствие новой защищённой
операции того же thread на том же соединении. Если чат уже заново занят,
старое намерение очистки отменяется: отписка действует на thread, а не на старый
turn. Никогда не посылать очистку старой generation в новое соединение.
Все решения сериализовать существующим `syncMu`, сохранив порядок блокировок.

### Очистка и восстановление

На каждом reconcile сравнивать известные poll-подписки с нужными активными
наблюдениями; очищать также записи удалённых/cleanup-топиков. Это не зависит от
успеха удаления Telegram-топика. На Sync off снимать ненужные poll-подписки,
сохраняя существующий drain активной локальной работы и независимый board flow.

При reconnect сбрасывать только учёт старого соединения и восстанавливать
подписки по свежему чтению, а не по всему списку топиков. Не повторять prompt.
При штатном shutdown выполнить ограниченную по времени очистку известных своих
подписок до закрытия соединений; отменённый run context не использовать для RPC.
Обрыв соединения остаётся отдельным путём восстановления, без новых гарантий
доставки старых approvals и без удаления истории.

Для обновления демона достаточно обычного перезапуска его соединений. Старые
подписки принадлежат прежнему клиенту; процессы MCP не следует массово убивать.
Отсутствие быстрой разгрузки само по себе не ошибка: учитывать grace period,
активность и других подписчиков App Server.

## Изменяемые места

- `internal/control/control.go`: обязательный `ThreadUnsubscribe(ctx, threadID)`
  в контракте Threads; `internal/appserver/client.go`: один RPC, проверка ответа.
  `unsubscribed`, `notSubscribed`, `notLoaded` означают достигнутую цель;
  неизвестный ответ и RPC error не скрывать.
- `internal/daemon/sync.go`, `service.go`: poll lifecycle, reconnect/off/shutdown,
  вызов writer cleanup и повторных попыток. При необходимости один небольшой
  `sync_subscriptions.go` для этой логики, без нового слоя или публичного API.
- `board_snapshot.go`, `external_dispatch.go`, `sync_draft.go`: проверить все
  terminal/abort callers и подключить очистку там, где уже есть известный thread.
  Защитные ветви unknown сохраняются.
- `test_helpers_test.go`: учёт unsubscribe/error и connection identity;
  существующие embedded fakes наследуют метод.
- Клиентские и daemon-тесты; ADR-034, contract matrix и regression map после
  реализации описывают новые правила наблюдения и задержку первого обнаружения.

## Последовательность реализации и проверки

1. Зафиксировать failing-регрессии: 100 idle-топиков дают ноль resume;
   active/waiting подписывается один раз; terminal отписывается и не загружается
   следующим sweep; reconnect восстанавливает только необходимые подписки.
2. Добавить RPC и контрактный тест payload/трёх успешных статусов/ошибки.
   Изменить poll-решение, подключить очистку топиков, off и reconnect.
3. Завершить writer lifecycle и abort callers. Добавить тест двух параллельных
   чатов: завершение одного снимает только его подписку. Ошибки cleanup повторяются,
   но не теряют Final; старый повтор не отписывает новый ход/новую generation.
4. Проверить desktop-ход между опросами, гонку read/resume/terminal и уже законченный
   короткий ход; ожидание approval/input, unknown dispatch, event gap и неудачное
   чтение. Проверить off/drain, cleanup-топик, shutdown и восстановление без replay.
   Сохранить существующие multipart delivery и stale callback regression suites.
5. Выполнить целевые тесты, `go test ./...`, race-тесты затронутого lifecycle,
   `go build -buildvcs=false ./...`, `git diff --check` и обязательный local/secret
   scan из AGENTS. Для существенного diff получить fresh-context review по правилам
   проекта. Обновить эксплуатационные документы.
6. При отдельно запрошенном развёртывании проверить реальный Telegram-контур:
   desktop → topic, Telegram → prompt/steer, approval/input, Final и следующий ход.
   Перед тестовыми сообщениями требуется явное разрешение на отправку.
   Дополнительно в изолированном App Server с тестовым MCP дождаться >30 минут
   без активности и других подписчиков: получить thread/closed и исчезновение
   дочерних MCP. В рабочем сервере сравнивать состав loaded threads и процессов,
   учитывая чужие подписки; не обещать фиксированное число освобождённых гигабайт.

Минимальное полезное приращение для поставки — пункты 1–5 вместе: одна законченная
правка lifecycle. Не выкатывать вариант, который только убрал resume или отписывает
terminal, но снова подписывает idle в следующем цикле.

## Ponytail-проверка и оценка LOC

Выбран текущий reconcile и текущие два соединения. Убраны из объёма универсальный
subscription manager, постоянное хранение подписок, новый poller, TTL в codex-tg,
новая настройка, принудительный unload, перезапуск App Server и смена MCP транспорта.
Одной правки конфигурации MCP недостаточно: она не устраняет удержание чатов и
других помощников. Сливать poll и writer дороже и рискованнее для ownership.

Карта неудачных writer-отписок оставлена: иначе ошибка RPC либо удерживает
завершённую работу, либо теряет намерение освободить ресурс. Для poll новая карта
не нужна — используется существующее множество подписок.

| Часть | Новые и изменённые строки, ориентир |
| --- | ---: |
| RPC и интерфейс | 20–35 |
| Poll: решение, catch-up и освобождение | 100–150 |
| Writer cleanup и безопасный повтор | 60–100 |
| Off/reconnect/shutdown и callers | 25–45 |
| **Рабочий код** | **205–330** |
| Тесты и fixtures | 250–400 |
| Обновление эксплуатационной документации | 40–60 |
| **Итого** | **примерно 500–800** |

Оценка относится к изменённым строкам, а не к чистому приросту. Готовых новых
модулей/зависимостей не требуется. Значимых продуктовых развилок перед кодированием
нет; минутная задержка первого наблюдения desktop-хода явно включена в дизайн.
Live Telegram и длительная выгрузка после grace period проверяются отдельно.
Приведённая выше оценка сделана до реализации; результаты находятся ниже.

## Уточнения при реализации

- Сохранён исходный RuntimeStatus: прежняя нормализация могла превратить
  notLoaded в статус незавершённого исторического хода. При противоречии между
  metadata и последним ходом перед отпиской выполняется одно чтение metadata.
- Множество poll-подписок стало картой attempted/confirmed; timeout resume не
  теряет возможную удалённую подписку. Дополнительная очередь не понадобилась.
- Ошибки записи проекции теперь возвращаются вызывающему коду; terminal cleanup
  не опережает сохранение Final. Подтверждение terminal receipt повторяется даже
  после успешной доставки Final, в том числе для board continuation.
- Обновлён один старый тест: общий каталог заменён на t.TempDir, поскольку
  race-прогон выявил зависимость от существования внешнего временного пути.

## Результаты проверки реализации

- Первые regression-тесты воспроизвели дефект: 100 idle-топиков вызывали 100 resume.
- Финальный `go test -p 1 ./... -count=1` прошёл для всех пакетов.
- Финальный `go test -race -p 1 ./internal/daemon ./internal/appserver ./internal/control -count=1` прошёл.
- `go build -buildvcs=false ./...`, `git diff --check`, обязательный поиск
  секретов/локальных данных и проверка новых файлов прошли.
- Независимый read-only reviewer проверил diff, план, ADR и regression-тесты.
  Замечания о durable Final и повторе terminal receipt исправлены и покрыты
  SQLite failure fixtures; оставшихся существенных замечаний нет.
- Рабочий демон не переустанавливался и не перезапускался. Live Telegram не
  проверялся: изменения пока не развёрнуты, тестовые сообщения не отправлялись.
- Изолированная проверка Codex 0.166.0 прошла: три ephemeral-чата создали три
  тестовых MCP, после unsubscribe и 32 минут без активности loaded/list вернул
  пустой список, все три MCP завершились. Штатное закрытие тестового сервера
  также оставило ноль дочерних fixture-процессов. Модель не вызывалась, рабочие
  чаты не затрагивались.

Фактический diff рабочего Go-кода: +278/-35 строк на момент проверки; тестов
и фикстур +564/-9. Увеличение тестового объёма относительно оценки связано с
выявленными сценариями отказа SQLite и гонками lifecycle. Экономия RAM на рабочем
контуре до развёртывания не измеряется.
